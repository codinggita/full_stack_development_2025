# Node.js Interview Questions & Answers

## Q1. What is Node.js and where can you use it?

Node.js is a runtime environment that lets JavaScript run outside the browser (e.g., on a server), built on Google's V8 engine. It's used for building backend APIs, real-time applications (chat apps, live notifications), command-line tools, microservices, and streaming applications.

---

## Q2. Why is Node.js single-threaded?

Node.js is single-threaded to keep things simple and efficient. It uses an event loop and non-blocking I/O to handle many requests at once without creating a new thread for each one.

**Important nuance (a common interview follow-up):** not all async operations work the same way under the hood.
- **Network I/O** (TCP/UDP sockets, most HTTP requests) doesn't use a thread pool at all — it's handled by the operating system's native async mechanisms (`epoll` on Linux, `kqueue` on macOS, IOCP on Windows), which notify the event loop when data is ready.
- The **libuv thread pool** (default size: 4 threads) is used only for operations that lack native OS-level async support — mainly **file system calls** (`fs` module), `dns.lookup()`, and CPU-heavy `crypto`/`zlib` operations. These are offloaded to worker threads in the pool so they don't block the main thread.

**Example:** if 100 users make API calls to a Node.js server, it won't create 100 threads. Instead, it handles them asynchronously on a single main thread — network requests via the OS's async I/O, and any file/crypto work via the small libuv thread pool — which saves memory and increases throughput.

---

## Q3. Explain callbacks in Node.js.

A callback is a function passed to another function that gets executed after an asynchronous task completes. It's how Node handles non-blocking I/O. For example, when reading a file with `fs.readFile`, the callback runs once the file is read, without stopping execution of other code.

Using too many nested callbacks can lead to **callback hell**, which is why Promises or async/await are preferred in modern code.

---

## Q4. What are the advantages of using Promises instead of callbacks?

Promises provide a cleaner, more manageable way to handle asynchronous operations. They help avoid callback hell, simplify error handling with `.catch()`, and make it easy to chain multiple operations sequentially.

## Q5. What is NPM?

**NPM (Node Package Manager)** is the default package manager for Node.js, used to install, manage, and share JavaScript packages.

## Q6. What are Modules in Node.js?

A module is a reusable block of code (functions, objects, or values) encapsulated in its own file, which can be imported and used elsewhere in a Node.js application.

**Three types of modules:**
1. **Built-in (core) modules** — come bundled with Node.js, e.g., `fs`, `http`, `path`, `os`, `events`.
2. **User-defined (local) modules** — files you create yourself in your project.
3. **Third-party modules** — installed via npm, e.g., `express`, `axios`, `mongoose`.

Node.js uses the **CommonJS** module system by default:
```js
// math.js
function add(a, b) { return a + b; }
module.exports = add;

// app.js
const add = require('./math');
console.log(add(2, 3)); // 5
```

Modern Node also supports **ES Modules** (`import`/`export`) when using the `.mjs` extension or `"type": "module"` in `package.json`.

## Q7. What is Event-Driven Programming?

A programming paradigm where the flow of the program is determined by events — user actions, I/O operations like reading files, or receiving HTTP requests. Instead of running strictly line by line, the program waits for events and responds with callback functions or event handlers.

---

## Q8. What is the Event Loop in Node.js?

The Event Loop is the core mechanism that lets Node.js perform non-blocking I/O despite being single-threaded. It offloads I/O tasks (file system, network, timers) to the system/libuv thread pool, and processes their callbacks once the tasks complete — without blocking the main thread.

**The event loop runs through distinct phases, in order, on every iteration ("tick"):**

| Phase | What runs here |
|---|---|
| **Timers** | Callbacks scheduled by `setTimeout()` and `setInterval()` |
| **Pending callbacks** | I/O callbacks deferred from the previous cycle |
| **Poll** | Retrieves new I/O events; executes I/O-related callbacks |
| **Check** | Callbacks scheduled via `setImmediate()` |
| **Close callbacks** | Cleanup callbacks, e.g., `socket.on('close', ...)` |

Additionally, **microtasks** — Promise callbacks (`.then`) and `process.nextTick()` — run *between* each phase, with `process.nextTick()` given even higher priority than Promise microtasks.

`package.json` is a metadata file present in every Node.js project. It manages the project's dependencies, scripts, version, entry point, and other configuration — acting as the project's blueprint.

## Q10. What is Express.js?

Express.js is a minimal web framework for Node.js. It simplifies building web servers and APIs by providing built-in methods for routing, handling requests/responses, and managing middleware.

---

## Q11. What is Middleware in Express?

Middleware is a function that has access to the `req` (request), `res` (response), and `next()` function in the app's request-response cycle. It's used to process requests before they reach the final route handler.

**Syntax:**
```js
function middleware(req, res, next) {
  // Do something with req/res
  next(); // Pass control to the next middleware or route
}
```

**Types of middleware:**
1. **Application-level** — attached to the `app` object, runs for all or specific routes.
2. **Route-level** — applied to specific routes only.
3. **Built-in** — provided by Express (e.g., `express.json()`, `express.urlencoded()`).
4. **Error-handling** — takes 4 arguments: `(err, req, res, next)`.
5. **Third-party** — external packages like `cors`, `morgan`, `helmet`.

## Q12. Difference between CommonJS (`require`) and ES Modules (`import`).

| | CommonJS | ES Modules |
|---|---|---|
| Syntax | `require()` / `module.exports` | `import` / `export` |
| Loading | Synchronous, resolved at runtime | Asynchronous, statically analyzed at compile time |
| File extension | `.js` (default in Node) | `.mjs`, or `.js` with `"type": "module"` in `package.json` |
| `this` at top level | Refers to `module.exports` | `undefined` |
| Tree-shaking | Not supported | Supported (helps bundlers eliminate unused code) |

```js
// CommonJS
const fs = require('fs');
module.exports = myFunction;

// ES Modules
import fs from 'fs';
export default myFunction;
```

You can't freely mix the two in the same file — Node determines which system to use based on the file extension or the `"type"` field in `package.json`.

## Q13. What is the `fs` module? Sync vs Async methods.

The `fs` (File System) module lets Node.js read, write, update, delete, and watch files and directories.

**Async (non-blocking) — preferred in production:**
```js
const fs = require('fs');
fs.readFile('file.txt', 'utf8', (err, data) => {
  if (err) throw err;
  console.log(data);
});
```

**Sync (blocking) — simpler but halts the event loop until done:**
```js
const data = fs.readFileSync('file.txt', 'utf8');
console.log(data);
```

Async methods are generally preferred for server code since sync methods block the single thread, freezing all other requests until the operation completes. `fs.promises` (or `fs/promises`) also provides a Promise-based API for use with async/await.

## Q14. What are Streams and Buffers in Node.js?

**Buffer** — a fixed-size chunk of memory used to handle raw binary data (e.g., data read from a file or network before it's fully processed). Unlike JS strings, buffers work directly with bytes.

```js
const buf = Buffer.from('Hello');
console.log(buf); // <Buffer 48 65 6c 6c 6f>
```

**Stream** — an abstraction for working with data that's read or written piece-by-piece (in chunks) rather than loading it all into memory at once — essential for handling large files or data over a network efficiently.

**Four types of streams:**
1. **Readable** — data can be read from it (e.g., `fs.createReadStream`).
2. **Writable** — data can be written to it (e.g., `fs.createWriteStream`).
3. **Duplex** — both readable and writable (e.g., a TCP socket).
4. **Transform** — a duplex stream that can modify data as it passes through (e.g., `zlib` compression).

```js
const fs = require('fs');
const readStream = fs.createReadStream('large-file.txt');
const writeStream = fs.createWriteStream('copy.txt');
readStream.pipe(writeStream); // efficiently streams data chunk by chunk
```

## Q15. What is the `process` object? What is `NODE_ENV`?

`process` is a global object in Node.js that provides information about, and control over, the current running Node process.

**Common uses:**
```js
process.env.NODE_ENV       // read environment variables
process.argv                // command-line arguments
process.exit(1)             // exit the process with a status code
process.on('exit', () => {}) // listen for process events
```

**`NODE_ENV`** is a conventional environment variable used to indicate the running environment — typically `development`, `production`, or `test`. Many libraries (like Express) change behavior based on it (e.g., disabling verbose error stack traces in production).

Environment-specific secrets/config (API keys, DB URLs) are commonly managed with a `.env` file and the `dotenv` package:
```js
require('dotenv').config();
console.log(process.env.DB_URL);
```

## Q16. What is the `EventEmitter` class?

`EventEmitter` (from the built-in `events` module) is the foundation of Node's event-driven architecture. It lets objects emit named events and register listeners that respond to them — many core Node APIs (streams, HTTP servers) are built on top of it.

```js
const EventEmitter = require('events');
const emitter = new EventEmitter();

emitter.on('greet', (name) => {
  console.log(`Hello, ${name}!`);
});

emitter.emit('greet', 'Alice'); // "Hello, Alice!"
```

## Q17. What are `child_process` and the `cluster` module?

**`child_process`** — lets Node.js spawn new OS-level processes to run other programs or scripts, useful for CPU-intensive tasks or running shell commands without blocking the main event loop.

```js
const { exec } = require('child_process');
exec('ls -la', (err, stdout) => console.log(stdout));
```
Methods include `exec()`, `spawn()`, `fork()` (specifically for spawning Node.js processes), each with different tradeoffs around buffering and streaming output.

**`cluster` module** — lets you take advantage of multi-core systems by spawning multiple Node.js worker processes (each with its own event loop) that share the same server port, distributing incoming connections across them.

```js
const cluster = require('cluster');
const os = require('os');

if (cluster.isPrimary) {
  os.cpus().forEach(() => cluster.fork());
} else {
  require('./server'); // each worker runs the actual server
}
```

---

## Q18. What are `worker_threads`?

The `worker_threads` module allows running JavaScript in parallel on separate threads within the same process — unlike `child_process`, workers can share memory (via `SharedArrayBuffer`) and have lower overhead. Useful for CPU-intensive tasks (heavy computation, image processing) that would otherwise block the single main thread.

```js
const { Worker } = require('worker_threads');
const worker = new Worker('./heavy-task.js');
worker.on('message', (result) => console.log(result));
```

**Key distinction:** `cluster` is for scaling I/O-bound work (multiple server instances); `worker_threads` is for offloading CPU-bound work within a single app instance.

## Q19. How is error handling done in Node.js?

**With async/await:**
```js
async function getData() {
  try {
    const data = await fetchData();
  } catch (err) {
    console.error('Error:', err);
  }
}
```

**Unhandled Promise rejections** — if a Promise rejects and there's no `.catch()`, Node emits an `unhandledRejection` event:
```js
process.on('unhandledRejection', (reason) => {
  console.error('Unhandled rejection:', reason);
});
```

**Uncaught synchronous exceptions:**
```js
process.on('uncaughtException', (err) => {
  console.error('Uncaught exception:', err);
  process.exit(1); // recommended: exit after logging, since app state may be corrupted
});
```

Best practice: use these process-level handlers only as a last-resort safety net for logging/graceful shutdown — not as a substitute for proper `try/catch` and `.catch()` handling throughout the app.

## Q20. What are the basics of REST API design, JWT authentication, and Sessions vs Tokens?

**REST API basics:**
- Resources are represented by URLs (e.g., `/users/:id`).
- Standard HTTP methods map to CRUD: `GET` (read), `POST` (create), `PUT`/`PATCH` (update), `DELETE` (remove).
- Stateless — each request contains all the information needed; the server doesn't store client session state between requests.
- Appropriate status codes: `200` OK, `201` Created, `400` Bad Request, `401` Unauthorized, `404` Not Found, `500` Server Error.

**JWT (JSON Web Token) authentication:**
A JWT is a signed token (header, payload, signature) issued to a user after login, which the client then sends with subsequent requests (usually in an `Authorization: Bearer <token>` header) to prove their identity — without the server needing to look up a session on every request.

```js
const jwt = require('jsonwebtoken');
const token = jwt.sign({ userId: 123 }, 'secretKey', { expiresIn: '1h' });
const decoded = jwt.verify(token, 'secretKey');
```

**Sessions vs Tokens:**
| | Sessions | Tokens (JWT) |
|---|---|---|
| State | Stored server-side (in memory/DB), client holds a session ID | Self-contained; server doesn't store anything |
| Scalability | Harder to scale across multiple servers (needs shared session store) | Easier — any server can verify the token independently |
| Revocation | Easy (just delete the session) | Harder (token is valid until it expires, unless you maintain a blocklist) |

## Q21. What is CORS, Rate Limiting, and Security Middleware like `helmet`?

**CORS (Cross-Origin Resource Sharing)** — a browser security mechanism that blocks web pages from making requests to a different origin than the one that served the page, unless the server explicitly allows it. In Express:
```js
const cors = require('cors');
app.use(cors({ origin: 'https://example.com' }));
```

**Rate limiting** — restricts how many requests a client can make in a given time window, to prevent abuse/DDoS and control server load.
```js
const rateLimit = require('express-rate-limit');
app.use(rateLimit({ windowMs: 15 * 60 * 1000, max: 100 })); // 100 requests per 15 min
```

**`helmet`** — a middleware that sets various HTTP security headers automatically (e.g., preventing clickjacking, disabling MIME-sniffing, setting a Content-Security-Policy), hardening an Express app against common web vulnerabilities.
```js
const helmet = require('helmet');
app.use(helmet());
```

## Q22. How do you connect Node.js to a database (MongoDB/Mongoose, SQL/ORMs)?

**MongoDB with Mongoose (ODM):**
```js
const mongoose = require('mongoose');
mongoose.connect('mongodb://localhost:27017/mydb');

const userSchema = new mongoose.Schema({ name: String, age: Number });
const User = mongoose.model('User', userSchema);

const newUser = await User.create({ name: 'Alice', age: 25 });
```

**SQL with an ORM (e.g., Sequelize or Prisma):**
```js
// Prisma example
const { PrismaClient } = require('@prisma/client');
const prisma = new PrismaClient();

const user = await prisma.user.create({
  data: { name: 'Alice', age: 25 },
});
```

**ORM/ODM benefits:** write database queries using JavaScript objects/methods instead of raw SQL, get schema validation, and simplify handling relationships between models — at the cost of some performance overhead and less control over the exact query generated versus hand-written SQL.

## Q23. Difference between `dependencies` and `devDependencies`; what is `package-lock.json`?

- **`dependencies`** — packages required for the app to run in production (e.g., `express`, `mongoose`).
- **`devDependencies`** — packages only needed during development (e.g., `nodemon`, `jest`, `eslint`), not installed in a production build if you run `npm install --production`.

```bash
npm install express          # adds to dependencies
npm install --save-dev jest  # adds to devDependencies
```

**Semantic Versioning (semver)** — package versions follow `MAJOR.MINOR.PATCH` (e.g., `4.18.2`):
- `^4.18.2` — allows minor/patch updates (up to but not including `5.0.0`).
- `~4.18.2` — allows only patch updates (up to but not including `4.19.0`).

**`package-lock.json`** — automatically generated file that locks the exact resolved version of every installed package (including nested dependencies), ensuring everyone on the team and every deployment installs identical versions — even if `package.json` specifies flexible version ranges.

## Q24. What are the basics of Testing (Jest/Mocha) and Process Managers (PM2) in Node.js?

**Testing with Jest:**
```js
function add(a, b) { return a + b; }

test('adds 2 + 3 to equal 5', () => {
  expect(add(2, 3)).toBe(5);
});
```

**Mocha** (often paired with the `chai` assertion library) works similarly but with a slightly different API and requires assertion/mocking libraries to be added separately, whereas Jest bundles them together out of the box.

**PM2** — a production process manager for Node.js applications. It keeps apps running continuously (auto-restarting on crashes), supports zero-downtime reloads, load balancing across CPU cores (similar in spirit to the `cluster` module but managed for you), and log management.

```bash
pm2 start app.js --name my-app
pm2 restart my-app
pm2 logs my-app
pm2 startup   # auto-start app on server reboot
```
