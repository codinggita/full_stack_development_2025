# 25. Logging & Monitoring

Logging and monitoring help identify errors, performance problems, and unexpected behavior in Next.js applications — during development and in production.

---

# 1. Structured Logging

Logging means recording useful information about what an application is doing.

Examples:

```text
User logged in
Product created
Database query failed
Payment request failed
```

Production logs should help answer:

```text
What happened?
When did it happen?
Which request caused it?
Where did it fail?
What was the error?
```

A structured log can look like:

```json
{
  "level": "info",
  "event": "product.created",
  "requestId": "req_123",
  "userId": "user_456",
  "productId": "product_789",
  "timestamp": "2026-08-18T12:00:00.000Z"
}
```

---

# 2. Why `console.log()` Is Not Enough

During development:

```ts
console.log("User created");
```

is perfectly useful.

In production, however, applications need:

- Consistent log structure
- Log levels
- Request correlation
- Search and filtering
- Centralized storage
- Error context

Instead of:

```text
User created product 123
```

prefer structured information:

```json
{
  "event": "product.created",
  "productId": "123",
  "userId": "456"
}
```

---

# 3. Log Levels

Common log levels include:

```text
TRACE
DEBUG
INFO
WARN
ERROR
FATAL
```

A practical application commonly uses:

```text
DEBUG
INFO
WARN
ERROR
```

## 3.1 DEBUG

Detailed information useful during development.

```ts
logger.debug({
  productId,
}, "Fetching product");
```

## 3.2 INFO

Normal important application events.

```ts
logger.info({
  userId,
  productId,
}, "Product created");
```

## 3.3 WARN

Unexpected situations that do not necessarily mean failure.

```ts
logger.warn({
  durationMs: 3200,
}, "Slow database query");
```

## 3.4 ERROR

Failures requiring investigation.

```ts
logger.error({
  err,
  requestId,
}, "Failed to create order");
```

---

# 4. What Should a Log Contain?

Useful fields commonly include:

```text
Timestamp
Log level
Event/message
Request ID
User ID when appropriate
Route
HTTP method
Status code
Duration
Resource ID
Error information
Environment
Release/version
```

Example:

```json
{
  "level": "info",
  "event": "http.request.completed",
  "requestId": "req_abc123",
  "method": "GET",
  "route": "/api/products",
  "statusCode": 200,
  "durationMs": 84
}
```

Do not log everything automatically. Log information that is useful and safe.

---

# 5. What Should NOT Be Logged?

Never casually log:

```text
Passwords
Authentication tokens
Session secrets
API keys
Private keys
Credit card information
Sensitive personal information
```

Bad:

```ts
logger.info({
  email,
  password,
}, "Login attempt");
```

Better:

```ts
logger.info({
  userId,
}, "Login successful");
```

Be especially careful with request bodies, cookies, and authorization headers.

---

# 6. Event-Based Logging

Avoid vague messages:

```ts
logger.info("Something happened");
```

Prefer meaningful events:

```ts
logger.info({
  event: "product.created",
  userId,
  productId,
});
```

Examples:

```text
user.registered
user.logged_in
product.created
order.created
payment.completed
payment.failed
http.request.completed
```

A consistent naming convention makes logs easier to search.

---

# 7. Request Logging

For backend requests, useful information includes:

```text
Request ID
HTTP method
Route
Status code
Duration
```

Example:

```json
{
  "level": "info",
  "event": "http.request.completed",
  "requestId": "req_123",
  "method": "POST",
  "route": "/api/products",
  "statusCode": 201,
  "durationMs": 145
}
```

---

# 8. Request IDs

A request ID is a unique identifier assigned to a request.

Example:

```text
req_7f92a
```

The same ID should be included in logs generated while processing that request.

```text
Request received
requestId = req_123

Validation completed
requestId = req_123

Database operation
requestId = req_123

Product created
requestId = req_123
```

---

# 9. Why Request IDs Matter

Suppose production receives:

```text
500 requests per second
```

One request fails.

Without a request ID:

```text
Which database error belongs to this request?
```

With a request ID:

```text
req_123
   ↓
HTTP request
   ↓
Service log
   ↓
Database error
   ↓
500 response
```

You can search all logs using:

```text
requestId = req_123
```

---

# 10. Request ID Flow

A typical request flow is:

```text
Client
   ↓
Next.js
   ↓
Request ID generated/read
   ↓
Route Handler
   ↓
Service
   ↓
Repository
   ↓
Database
```

Every relevant log can contain the same request ID.

---

# 11. Generating a Request ID

A simple implementation:

```ts
const requestId =
  crypto.randomUUID();
```

Then:

```ts
logger.info({
  requestId,
}, "Request started");
```

In larger deployments, infrastructure may already provide a correlation identifier.

---

# 12. Existing Request IDs

You may receive a request ID through a header:

```ts
const requestId =
  request.headers.get("x-request-id")
  ?? crypto.randomUUID();
```

Do not use an arbitrary client-provided ID for security decisions. It is a correlation value, not an authentication mechanism.

---

# 13. Returning the Request ID

It can be useful to return the request ID in an API response:

```ts
return Response.json(
  {
    message: "Internal server error",
    requestId,
  },
  {
    status: 500,
  }
);
```

The response can also include:

```http
x-request-id: req_123
```

Then support teams can ask users for the request ID when investigating a problem.

---

# 14. Request ID vs Trace ID

These concepts are related.

### Request ID

Usually identifies one logical request:

```text
req_123
```

### Trace ID

Identifies a distributed operation:

```text
trace_456
```

A trace may contain:

```text
Trace
 ├── Frontend request
 ├── API request
 ├── Database operation
 └── External API request
```

For distributed systems, tracing can provide more detail than a simple request ID.

---

# 15. Server Errors

Server-side errors can happen in:

```text
Server Components
Route Handlers
Server Actions
Database operations
External APIs
Background jobs
```

Example:

```ts
try {
  const product =
    await productService.create(data);

  return Response.json(
    product,
    { status: 201 }
  );
} catch (error) {
  logger.error({
    err: error,
    requestId,
  }, "Failed to create product");

  return Response.json(
    {
      message: "Internal server error",
      requestId,
    },
    { status: 500 }
  );
}
```

---

# 16. Do Not Expose Internal Errors

Bad:

```ts
return Response.json({
  error: error.message,
});
```

The error may reveal:

```text
Database details
Internal paths
SQL information
Service names
Implementation details
```

Better:

```ts
return Response.json(
  {
    message: "Internal server error",
    requestId,
  },
  { status: 500 }
);
```

Detailed information belongs in internal logs and error monitoring.

---

# 17. Server Error Handling Flow

A production error flow should look like:

```text
Unexpected error
      ↓
Catch / error boundary
      ↓
Log detailed error
      ↓
Capture in error monitoring
      ↓
Associate request ID
      ↓
Return safe response
```

This separates:

```text
Developer information
```

from:

```text
User information
```

---

# 18. Client Errors

Client-side errors occur in the browser.

Examples:

```text
JavaScript exception
Component crash
Failed interaction
Browser API failure
Unhandled promise rejection
```

These should be captured separately from server logs.

---

# 19. `error.tsx`

Next.js provides route-level error boundaries through:

```text
error.tsx
```

Example:

```tsx
"use client";

export default function ErrorPage({
  error,
  reset,
}: {
  error: Error & {
    digest?: string;
  };
  reset: () => void;
}) {
  return (
    <div>
      <h2>
        Something went wrong.
      </h2>

      <button onClick={() => reset()}>
        Try again
      </button>
    </div>
  );
}
```

The error boundary provides a user-friendly fallback UI.

---

# 20. Error Boundary vs Error Monitoring

These solve different problems.

### Error boundary

```text
Application error
   ↓
Show fallback UI
```

### Error monitoring

```text
Application error
   ↓
Capture error
   ↓
Send information to monitoring system
   ↓
Developer investigates
```

A production application can use both.

---

# 21. Error Monitoring

Error monitoring platforms collect and organize application failures.

Examples:

```text

```

A monitoring system can capture:

```text
Exception
Stack trace
Route
Browser
Operating system
Environment
Release/version
User context when appropriate
Breadcrumbs
```

Sensitive data must be filtered.

---

# 22. Logs vs Error Monitoring

They are complementary.

### Logs

Answer:

```text
What was the application doing?
```

### Error monitoring

Answers:

```text
What failed?
How often?
Where?
Which release?
How many users were affected?
```

For example:

```text
Logs:
Database query failed

Error monitoring:
142 users affected
Issue started after release 2.4.0
Most failures occur on /checkout
```

# 23. Error Context

An error becomes more useful when it contains safe context.

```json
{
  "error": "Database connection failed",
  "requestId": "req_123",
  "route": "/api/orders",
  "method": "POST",
  "environment": "production",
  "release": "2.4.0"
}
```

Do not include:

```text
Passwords
Tokens
Secrets
Payment credentials
```

# 24. Error Grouping

Monitoring platforms can group similar errors.

For example:

```text
Cannot read properties of undefined
```

may happen hundreds of times.

The platform can group these into:

```text
Issue #123
Occurrences: 2,481
Users affected: 613
```

This helps developers prioritize the most important problems.

# 27. Request Duration

Suppose:

```text
GET /api/products
```

takes:

```text
85ms
```

Log:

```json
{
  "route": "/api/products",
  "durationMs": 85
}
```

This makes slow endpoints easier to identify.

---

# 28. Measuring Request Duration

A basic pattern:

```ts
const start = performance.now();

try {
  // request processing
} finally {
  const durationMs =
    performance.now() - start;

  logger.info({
    requestId,
    durationMs,
  }, "Request completed");
}
```

---

# 29. Slow Request Detection

You can define an application-specific threshold.

For example:

```text
< 500ms
    Normal

500ms–2000ms
    Investigate

> 2000ms
    Slow
```

The correct threshold depends on the endpoint.

Example:

```ts
if (durationMs > 2000) {
  logger.warn({
    requestId,
    durationMs,
  }, "Slow request");
}
```

# 30. Database Performance Monitoring

# 31. N+1 Queries

A common database performance problem:

```text
Fetch 100 products
    ↓
Fetch category for product 1
Fetch category for product 2
...
Fetch category for product 100
```

This can result in:

```text
1 + 100 queries
```

A better approach may fetch the required relation together.

Monitoring query counts and duration can help identify this problem.

# 42. Server vs Client Logging

Next.js has both server and client execution environments.

| Location | Typical logging destination |
|---|---|
| Server Component | Server logs |
| Route Handler | Server logs |
| Server Action | Server logs |
| Client Component | Browser console |
| Browser exception | Client error monitoring |
| Database | Database/system logs |

This is important because:

```text
console.log()
```

inside a Server Component does not appear in the browser console.

---

# 43. Logging in Server Components

Example:

```tsx
export default async function ProductsPage() {
  logger.info(
    "Loading products"
  );

  const products =
    await getProducts();

  return (
    <ProductList
      products={products}
    />
  );
}
```

This executes on the server.

Therefore the log belongs to the server environment.

---

# 44. Logging in Client Components

Example:

```tsx
"use client";

export function Button() {
  function handleClick() {
    console.log("Clicked");
  }

  return (
    <button onClick={handleClick}>
      Click
    </button>
  );
}
```

This runs in the browser.

For production client-side errors, use error monitoring instead of relying only on browser console output.

---

# 45. Logging in Route Handlers

Example:

```ts
export async function GET(
  request: Request
) {
  const requestId =
    request.headers.get("x-request-id")
    ?? crypto.randomUUID();

  const start = performance.now();

  try {
    const products =
      await productService.getAll();

    return Response.json(
      products,
      {
        headers: {
          "x-request-id": requestId,
        },
      }
    );
  } catch (error) {
    logger.error({
      err: error,
      requestId,
    }, "Failed to fetch products");

    return Response.json(
      {
        message: "Internal server error",
        requestId,
      },
      { status: 500 }
    );
  } finally {
    logger.info({
      requestId,
      durationMs:
        performance.now() - start,
    }, "Request completed");
  }
}
```

This demonstrates:

```text
Request ID
+
Error logging
+
Performance measurement
```

---

# 46. Logging in the Service Layer

Avoid logging every line:

```ts
logger.info("Entering function");
logger.info("Validation completed");
logger.info("Calling repository");
logger.info("Returning result");
```

This creates noise.

Prefer meaningful business events:

```ts
logger.info({
  userId,
  productId,
}, "product.created");
```

and meaningful failures:

```ts
logger.error({
  err: error,
  productId,
}, "product.creation_failed");
```

# 49. Release and Version Monitoring

Production deployments should ideally have a release/version identifier.

# 51. Good vs Bad Alerts

Good:


Bad:

A good alert should mean:


# 53. Percentile Latency

Average latency can hide slow requests.

Example:

```text
99 requests → 100ms
1 request   → 10 seconds
```

Useful percentiles include:

```text
P50 → median
P95 → 95% of requests are faster
P99 → 99% of requests are faster
```

For production APIs, P95 and P99 can be more useful than average latency alone.

```text
        └───────────┼───────────┘
                    ▼
              Observability
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
      Dashboard             Alerts
```

Key principles:

> **Log useful events, not everything.**

> **Use structured logs so machines can search and filter them.**

> **Use request IDs to connect logs belonging to the same request.**

> **Never expose sensitive information through logs or error responses.**

> **Monitor both errors and performance.**

> **Use error boundaries to protect the user experience and error monitoring to investigate failures.**

> **For distributed systems, combine request correlation with tracing when necessary.**

> **Good observability should answer not only "what failed?" but also "why did it fail?"**
