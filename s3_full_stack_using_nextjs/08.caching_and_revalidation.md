# 08. Caching & Revalidation

Caching is one of the important concepts in Next.js because it can reduce unnecessary work and make applications faster.

Instead of generating or fetching the same data again and again, Next.js can reuse previously generated or fetched results when the application's caching configuration allows it.

A simple idea is:

```text
Without caching

User Request
     ↓
Fetch data
     ↓
Render page
     ↓
Return response
```

With caching:

```text
User Request
     ↓
Check cache
     ↓
Cache available?
   /       \
 Yes        No
  ↓          ↓
Use cache  Fetch / render
             ↓
          Store result
```

Next.js has multiple caching layers. Each layer has a different purpose.

---

# 1. Caching in Next.js

Caching means storing a result so it can be reused later.

For example, suppose an application requests:

```text
/products
```

and the products rarely change.

Without caching:

```text
Request 1 → API
Request 2 → API
Request 3 → API
Request 4 → API
```

With caching:

```text
Request 1 → API → Cache

Request 2 → Cache
Request 3 → Cache
Request 4 → Cache
```

This can reduce:

- API requests
- Database queries
- Server work
- Response time

However, cached data can become outdated.

That is why caching is usually combined with **revalidation**.

```text
Caching
   +
Revalidation
   ↓
Fast + reasonably fresh data
```

> Next.js has changed caching behavior across major versions. The important concept is to understand what is being cached, where it is cached, and when it is revalidated rather than assuming that every request is automatically cached.

---

# 2. Caching Layers

For the App Router, it is useful to understand these caching layers:

```text
Next.js Application
│
├── a. Data Cache
│
├── b. Full Route Cache
│
├── c. Client Router Cache
│
└── d. Request Memoization
```

Each one solves a different problem.

| Cache                      | What it stores                               | Where it works |
| -------------------------- | -------------------------------------------- | -------------- |
| **a.** Data Cache          | Results of data requests                     | Server         |
| **b.** Full Route Cache    | Rendered route output                        | Server         |
| **c.** Client Router Cache | Route segments used during navigation        | Browser        |
| **d.** Request Memoization | Repeated identical requests during rendering | Server render  |

The first three are actual caching layers. Request Memoization is a request-level optimization that prevents duplicate work during a render.

---

## a. Data Cache

The **Data Cache** stores the result of data fetching so that the same data does not always have to be fetched again.

Conceptually:

```text
Server
  ↓
Fetch API / Data
  ↓
Data Cache
  ↓
Reuse cached result
```

Depending on the request's caching configuration and the Next.js version, the result may be cached and reused.

The important point is:

```text
Data Cache
    ↓
Caches fetched data
```

It is about the **data**, not the complete HTML page.

---

### Data Cache Example

Suppose you have:

```tsx
async function getProducts() {
	const response = await fetch("https://fakestoreapi.com/products");

	return response.json();
}
```

Conceptually:

```text
First request
     ↓
Fetch API
     ↓
Store result in Data Cache

Later request
     ↓
Check Data Cache
     ↓
Reuse data when cache configuration allows it
```

This can prevent repeated requests to the external API.

---

## b. Full Route Cache

The **Full Route Cache** stores the rendered result of a route on the server.

It is different from the Data Cache.

### Data Cache

Stores:

```text
Fetched data
```

### Full Route Cache

Stores:

```text
Rendered route output
```

Conceptually:

```text
Data
 ↓
Server Component rendering
 ↓
Rendered route
 ↓
Full Route Cache
```

For statically rendered routes, Next.js can reuse the rendered result instead of rendering the entire route again for every request.

---

## Data Cache vs Full Route Cache

Consider:

```tsx
const products = await getProducts();

return <ProductList products={products} />;
```

There are two different things that can be cached:

```text
API result
    ↓
Data Cache

Rendered page
    ↓
Full Route Cache
```

Think of it as:

```text
DATA CACHE
"What data did we fetch?"

FULL ROUTE CACHE
"What did we render for this route?"
```

This distinction is very important.

---

## c. Client Router Cache

The **Client Router Cache** is a client-side cache used by the Next.js App Router.

It stores previously visited or prefetched route segments in the browser during navigation.

Conceptually:

```text
Browser
   ↓
Next.js Router Cache
   ↓
Previously received route segments
```

This helps make navigation faster.

For example:

```text
User visits:

/home
   ↓
/products
   ↓
/profile
   ↓
/products
```

When navigating back to `/products`, Next.js can reuse cached route information when appropriate instead of always requesting everything again.

Without the Router Cache, every navigation would request the server again even for recently visited pages. With it, Next.js stores route segments in the browser and reuses them when appropriate — improving client-side navigation performance.

The Router Cache is different from the Data Cache and Full Route Cache because it exists on the **client/browser side**.

---

## d. Request Memoization

Request Memoization prevents the same request from being performed multiple times during a single server render when the request can be memoized.

Suppose two components request the same data:

```tsx
async function getProduct(id: number) {
	const response = await fetch(`https://fakestoreapi.com/products/${id}`);
	return response.json();
}

// Component A
const product = await getProduct(10);

// Component B
const product = await getProduct(10);
```

Without request memoization, the application could perform duplicate work.

Conceptually:

```text
Component A
     ↓
Request A
     ↓
   Result
     ↑
Request Memoization
     ↓
Component B
```

The important point is:

> Request Memoization is about avoiding duplicate work during a render. It is not the same as persistent data caching.

---

## Request Memoization vs Data Cache

These concepts are often confused.

### Request Memoization

```text
Same render
    ↓
Avoid duplicate request
```

### Data Cache

```text
Across requests / render executions
    ↓
Reuse cached data when configured
```

Simple comparison:

| **d.** Request Memoization             | **a.** Data Cache                                                 |
| -------------------------------------- | ----------------------------------------------------------------- |
| Avoids duplicate work during rendering | Stores reusable fetched data                                      |
| Request/render-level optimization      | Persistent caching layer                                          |
| Short-lived                            | Can survive across requests depending on deployment/configuration |
| Prevents duplicate requests            | Can prevent fetching the data again                               |

---

# 3. Cache Behavior

Caching behavior depends on:

- What is being cached
- Whether the data is configured to be cached
- Whether the route is static or dynamic
- Revalidation settings
- Next.js version
- The APIs used by the route

Therefore, do not use this oversimplified rule:

```text
fetch() = always cached
```

or:

```text
fetch() = never cached
```

The exact behavior depends on the application's configuration and the Next.js version.

The important questions are:

```text
What is being cached?
        ↓
How long should it stay cached?
        ↓
What should invalidate it?
```

## Fetch Cache Options

You control Data Cache behavior through the `cache` option on `fetch`:

```tsx
// Static — cache indefinitely (default for many fetches)
fetch("https://fakestoreapi.com/products", { cache: "force-cache" });

// ISR — cache and revalidate on a timer
fetch("https://fakestoreapi.com/products", { next: { revalidate: 60 } });

// Dynamic — never cache; fetch on every request
fetch("https://fakestoreapi.com/products", { cache: "no-store" });
```

| Option                    | Effect                                           |
| ------------------------- | ------------------------------------------------ |
| `cache: "force-cache"`    | Reuse cached data; route stays static            |
| `next: { revalidate: N }` | Reuse cached data; refresh after N seconds (ISR) |
| `cache: "no-store"`       | Skip cache; route becomes dynamic                |

## Caching and Rendering

Caching choices directly affect whether a route is **static** or **dynamic** (see **Rendering**):

```text
force-cache / revalidate  →  Static Rendering / ISR
no-store                  →  Dynamic Rendering
```

Using `cache: "no-store"` is how you explicitly opt a fetch — and usually the route — out of caching when data must be fresh on every request.

## Newer Cache Model (Callout)

> Next.js also has a newer cache model using `'use cache'`, `cacheLife()`, and `cacheTag()`. The fetch-based approach used in these examples still works, but current docs and tutorials also show the newer style.

# 4. Revalidation

## Cache Lifetime

Cached data should not always remain unchanged forever.

For example:

```text
Product catalog
```

might change every:

```text
10 minutes
```

while:

```text
Company information
```

might change only once a month.

This is where **revalidation** becomes useful — telling the cache that stored data should no longer be trusted and needs to be refreshed on the next use.

```text
Cache
  ↓
Reuse data
  ↓
Revalidate after some condition
  ↓
Next visit fetches / generates fresh data
```

---

## Time-Based Revalidation

**Time-based revalidation** means allowing cached data to be reused for a specific amount of time before it becomes eligible for revalidation.

For example:

```text
Cache lifetime = 60 seconds
```

Conceptually:

```text
0 sec
 ↓
Cache fresh

30 sec
 ↓
Reuse cached data

60 sec
 ↓
Revalidation becomes necessary
```

This is useful when data changes occasionally but does not need to be updated on every request.

Examples:

```text
Product catalog
News listing
Weather information
Public statistics
Blog content
```

---

## `revalidate`

Next.js provides the `revalidate` option for controlling time-based revalidation.

For example:

```tsx
const response = await fetch("https://fakestoreapi.com/products", {
	next: {
		revalidate: 60,
	},
});

const products = await response.json();
```

This expresses the intention that the fetched data can be revalidated periodically.

The value:

```text
60
```

means:

```text
60 seconds
```

Conceptually:

```text
Fetch data
    ↓
Cache data
    ↓
Revalidate after 60 seconds
```

---

## Route-Level `revalidate`

A route can also define a revalidation interval.

For example:

```tsx
export const revalidate = 60;
```

Conceptually:

```text
Route
  ↓
Revalidate periodically
  ↓
Fresh route/data when required
```

This is useful when the route has a known freshness requirement.

For example:

```text
Blog page
    ↓
Revalidate every 3600 seconds
    ↓
1 hour
```

The exact caching behavior depends on the route and data-fetching configuration.

---

## Choosing a Revalidation Time

Do not choose a random value.

Think about how frequently the data changes.

| Data                     |           Example Revalidation |
| ------------------------ | -----------------------------: |
| Company information      |                           Long |
| Blog posts               |                         1 hour |
| Product catalog          |                  10–60 minutes |
| News                     |                    Few minutes |
| Frequently changing data |                          Short |
| Real-time data           | Usually not time-based caching |

The goal is:

```text
Longer cache
   ↓
Better performance
   ↓
Potentially older data
```

and:

```text
Shorter cache
   ↓
Fresher data
   ↓
More frequent work
```

---

## On-Demand Revalidation

Sometimes waiting for a timer is not the best solution.

Suppose an administrator updates a product:

```text
Product price:
₹999 → ₹799
```

You may want the cache to reflect the change without waiting for a timer.

Instead of waiting:

```text
Revalidate after 1 hour
```

you can trigger revalidation when the data changes.

This is called **on-demand revalidation**.

> **Important:** `revalidatePath()` and `revalidateTag()` do **not** update the cache the instant you call them. They mark cached content as stale. Fresh data is fetched the **next time** that path or tag is visited.

Conceptually:

```text
Update data
    ↓
Call revalidatePath() or revalidateTag()
    ↓
Cache marked stale
    ↓
Next visit to path/tag → fresh data fetched
```

---

## `revalidatePath`

`revalidatePath()` marks a route's cached output as stale so it can be regenerated on the **next visit** to that path.

Import it from:

```tsx
import { revalidatePath } from "next/cache";
```

Example:

```tsx
"use server";

import { revalidatePath } from "next/cache";

export async function updateProduct() {
	// Update product in database

	revalidatePath("/products");
}
```

Signature:

```tsx
revalidatePath(path: string, type?: "page" | "layout")
```

- `"page"` (default) — revalidates the page at that path
- `"layout"` — also revalidates layouts that wrap the path (useful when a shared layout displays data from the mutation)

Example — a root layout shows total product count:

```tsx
revalidatePath("/products", "layout");
```

Conceptually:

```text
Update product
     ↓
revalidatePath("/products")
     ↓
/products cache marked stale
     ↓
Next visit to /products → fresh data rendered
```

This is useful when you know which route is affected by a data change.

---

## `revalidatePath` Example

Suppose:

```text
/products
```

shows all products.

An administrator updates a product:

```text
Admin
  ↓
Update product
  ↓
Database
  ↓
revalidatePath("/products")
  ↓
Next visit to /products → fresh data
```

Example:

```tsx
import { revalidatePath } from "next/cache";

export async function updateProduct(id: string, price: number) {
	await db.product.update({
		where: { id },
		data: { price },
	});

	revalidatePath("/products");
}
```

The database update and cache invalidation happen as two separate operations:

```text
Database → Update data

Cache → Mark route stale (refreshes on next visit)
```

---

## Revalidating a Dynamic Route

Suppose you have:

```text
/products/[id]
```

and want to revalidate:

```text
/products/123
```

You can specify the affected path:

```tsx
revalidatePath("/products/123");
```

Conceptually:

```text
Update Product 123
       ↓
revalidatePath("/products/123")
       ↓
Next visit to /products/123 → fresh data
```

---

## `revalidateTag`

Sometimes the same data is used by multiple routes.

For example:

```text
/products
/products/123
/search
/home
```

may all use product data.

If you only revalidate one path:

```tsx
revalidatePath("/products");
```

other routes that use the same product data may still have cached results.

A **cache tag** allows related cached data to be grouped conceptually.

Example:

```tsx
const response = await fetch("https://fakestoreapi.com/products", {
	next: {
		tags: ["products"],
	},
});

const products = await response.json();
```

Now the request is associated with:

```text
products
```

tag.

---

## Revalidating a Tag

After changing product data, you can mark tagged cache entries as stale:

```tsx
import { revalidateTag } from "next/cache";

export async function updateProduct() {
	// Update database

	revalidateTag("products", "max");
}
```

The second argument is a **cache profile**. `"max"` means **stale-while-revalidate**:

```text
revalidateTag("products", "max") called
        ↓
Old cached content still served immediately
        ↓
Fresh data fetched in the background
        ↓
Next visit gets the updated content
```

It does **not** mean "refresh the cache right now." The current response may still show stale data until the background revalidation completes and a subsequent visit occurs.

> **`revalidateTag("products")` with a single argument is deprecated.** Always pass the cache profile: `revalidateTag("products", "max")`.

The important concept:

```text
Tag → Group related cached data → Mark stale on mutation → Refresh on next use
```

---

## `updateTag` vs `revalidateTag`

For **BuildMart**, when an admin edits a product, they need to see the updated price **immediately** — not stale content while a background refresh runs.

| Function                    | When to use                            | Behavior                                           |
| --------------------------- | -------------------------------------- | -------------------------------------------------- |
| `revalidateTag(tag, "max")` | Background cache refresh across routes | Stale-while-revalidate; old content may still show |
| `updateTag(tag)`            | Server Actions after a mutation        | Expires cache immediately; read-your-own-writes    |

```text
revalidateTag  →  mark stale, refresh on next visit (background)
updateTag      →  immediate expiry, used in Server Actions after a mutation
```

`updateTag` can **only** be called inside a Server Action:

```tsx
"use server";

import { updateTag } from "next/cache";

export async function updateProduct(id: string, price: number) {
	await db.product.update({
		where: { id },
		data: { price },
	});

	updateTag("products"); // admin sees updated data immediately
}
```

Use `updateTag` when the person who made the change needs to see fresh data right away. Use `revalidateTag` when you want to invalidate shared cached data across many routes without requiring instant freshness.

---

## `revalidatePath` vs `revalidateTag`

These are both used for on-demand revalidation, but they solve different problems.

### `revalidatePath()`

Think:

```text
Which route should be revalidated?
```

Example:

```tsx
revalidatePath("/products");
```

### `revalidateTag()`

Think:

```text
Which group of cached data should be revalidated?
```

Example:

```tsx
revalidateTag("products", "max");
```

Comparison:

|                         | `revalidatePath()`          | `revalidateTag()`                                                 |
| ----------------------- | --------------------------- | ----------------------------------------------------------------- |
| Targets                 | A route/path                | Tagged cached data                                                |
| Orientation             | Route-oriented              | Data-oriented                                                     |
| Best when               | A specific page is affected | Data is shared by many pages                                      |
| Example                 | `/products`                 | `"products"`                                                      |
| When fresh data appears | Next visit to that path     | Next request using that tag (stale-while-revalidate with `"max"`) |

Neither function updates the cache the instant you call it — both mark content stale and refresh on subsequent use.

---

## Time-Based vs On-Demand Revalidation

There are two common approaches.

### Time-Based

```text
Cache
  ↓
Wait for configured time
  ↓
Revalidate
```

Example:

```tsx
next: {
  revalidate: 60,
}
```

Use this when:

```text
Data changes periodically
```

---

### On-Demand

```text
Data changes
   ↓
Call revalidatePath / revalidateTag / updateTag
   ↓
Cache marked stale (or expired for updateTag)
   ↓
Fresh data on next visit (or immediately for updateTag in same action)
```

Use on-demand revalidation when:

```text
You know exactly when the data changed
```

Consider an e-commerce application.

```text
Admin Dashboard
       ↓
Update Product (Server Action)
       ↓
Database
       ↓
updateTag("products")
       ↓
Admin sees updated data immediately
       ↓
Customer pages refresh on next visit
```

Suppose these pages use product data:

```text
/products
/products/123
/search
```

Tag the fetch:

```tsx
const response = await fetch("https://fakestoreapi.com/products", {
	next: {
		tags: ["products"],
	},

```

After updating a product in a Server Action:

```tsx
"use server";

	});

```

# 6. Example: Blog CMS

Suppose you have:

```text
/blog
/blog/nextjs-caching
```

A CMS administrator publishes a new article.

You do not want to wait for a scheduled revalidation.

You can trigger revalidation when publishing. Fresh content appears on the **next visit** to each path — not instantly when the function is called.

For example:

```tsx
revalidatePath("/blog");
```

and for the individual article:

```tsx
revalidatePath("/blog/nextjs-caching");
```

Or, if the application uses tags:

```tsx
revalidateTag("blog", "max");
```

The exact strategy depends on how the application's data is cached.

# 7. Caching Flow

A useful way to understand the complete system is:

```text
User Request
     ↓
c. Client Router Cache
     ↓
Server
     ↓
b. Full Route Cache
     ↓
a. Data Cache
     ↓
External API / Database
```

Not every request goes through every layer.

The layers have different responsibilities.

```text
c. Client Router Cache
        ↓
Browser navigation

a. Data Cache
        ↓
Fetched data

b. Full Route Cache
        ↓
Rendered route

d. Request Memoization
        ↓
Avoid duplicate requests during a render
```

# 8. Common Caching Mistakes

## Assuming Everything Is Cached

Do not assume:

```text
fetch()
   ↓
Always cached
```

Caching behavior depends on the Next.js version and configuration.

---

## Caching Data That Must Be Real-Time

For example:

```text
Bank account balance
Live trading price
Real-time chat
```

These may require fresher data than a normal time-based cache should provide.

---

## Choosing a Very Long Revalidation Time

Example:

```tsx
revalidate: 86400;
```

means:

```text
24 hours
```

If the data changes every 10 minutes, users could see outdated data.

Choose a value based on the data's freshness requirement.

---

## Revalidating the Wrong Path

Suppose the updated data appears on:

```text
/products
/search
/home
```

but you only revalidate:

```tsx
revalidatePath("/products");
```

The other routes may still have their own cached results.

If the same data is shared across many routes, consider a cache tag.

---

## Confusing Router Cache with Data Cache

They are not the same.

```text
Router Cache
    ↓
Client-side route segments

Data Cache
    ↓
Server-side fetched data
```

# 9. Best Practices

## Cache Data That Does Not Change Frequently

Good candidates:

```text
Product catalog
Blog posts
Documentation
Public configuration
Categories
```

---

## Use Appropriate Revalidation

Ask:

```text
How often does this data change?
```

Then choose an appropriate strategy.

```text
Rarely changes
    ↓
Longer cache

Changes periodically
    ↓
Time-based revalidation

Changes immediately after an action
    ↓
On-demand revalidation
```

---

## Use Tags for Shared Data

If the same data is used by many routes:

```text
/products
/products/123
/search
```

consider tagging the related data:

```tsx
tags: ["products"];
```

Then revalidate the tag after a mutation.

---

## Use Paths When a Specific Route Is Affected

If you know exactly which route needs fresh content:

```tsx
revalidatePath("/products");
```

is often straightforward.

---

## Keep Cache Strategy Simple

Do not introduce complicated caching rules without a reason.

Start with:

```text
What data?
     ↓
How often does it change?
     ↓
Who needs fresh data?
     ↓
Choose cache + revalidation strategy
```

# 10. Quick Reference

## Quick Comparison

| Concept                    | Main Purpose                                                |
| -------------------------- | ----------------------------------------------------------- |
| Caching                    | Reuse previous results                                      |
| **a.** Data Cache          | Cache fetched data                                          |
| **b.** Full Route Cache    | Cache rendered route output                                 |
| **c.** Client Router Cache | Cache route segments in the browser                         |
| **d.** Request Memoization | Avoid duplicate requests during a render                    |
| Time-Based Revalidation    | Refresh cache based on time                                 |
| On-Demand Revalidation     | Refresh cache when data changes                             |
| `revalidate`               | Configure time-based revalidation                           |
| `revalidatePath()`         | Mark a route stale; refreshes on next visit                 |
| `revalidateTag()`          | Mark tagged data stale; stale-while-revalidate with `"max"` |
| `updateTag()`              | Expire tagged cache immediately in Server Actions           |

---

## Simple Mental Model

Remember these four questions:

```text
1. What is cached?
        ↓
      a. Data / b. Route / c. Client Route / d. Memoization

2. Where is it cached?
        ↓
      Server / Browser

3. How long should it stay fresh?
        ↓
      Revalidation time

4. What happens when data changes?
        ↓
      updateTag (immediate) / revalidatePath / revalidateTag (on next visit)
```

# Summary

- Caching allows Next.js to reuse previously generated or fetched results.
- Caching can improve performance and reduce unnecessary server, API, and database work.
- **a. Data Cache** stores fetched data.
- **b. Full Route Cache** stores rendered route output.
- **c. Client Router Cache** stores route segments on the client for faster navigation.
- **d. Request Memoization** avoids duplicate requests during a server render.
- These caching mechanisms solve different problems and should not be treated as the same cache.
- Cache behavior depends on the Next.js version, APIs used, and caching configuration.
- `cache: "force-cache"`, `next: { revalidate }`, and `cache: "no-store"` control fetch caching and connect to static/dynamic rendering (Rendering).
- Time-based revalidation refreshes cached data according to a configured interval.
- On-demand revalidation marks cache stale when data changes — fresh data appears on the **next visit**, not instantly (unless using `updateTag`).
- `revalidatePath()` marks a route stale; optional second argument `"page" | "layout"` controls layout revalidation.
- `revalidateTag(tag, "max")` marks tagged data stale with stale-while-revalidate — single-argument form is **deprecated**.
- `updateTag()` expires tagged cache immediately in Server Actions — use after mutations when the user needs read-your-own-writes freshness.
- Use paths when the affected route is known; use tags when data is shared across routes.
- Choose caching based on how frequently data changes and how fresh it needs to be.

## Quick Decision Guide

```text
Does the data change rarely?
        ↓
Cache it
        ↓
Use an appropriate revalidation strategy

Does the data change periodically?
        ↓
Time-based revalidation
        ↓
revalidate

Does the data change immediately after an action?
        ↓
On-demand revalidation
        ↓
updateTag() in Server Actions (immediate)
or
revalidatePath() / revalidateTag() (on next visit)

Does the same data appear across many routes?
        ↓
Consider cache tags

Does only one route need to be refreshed?
        ↓
Consider revalidatePath()
```

> **Simple rule:** Cache data when it can be reused, choose a freshness period based on how often it changes, use `updateTag` when the mutating user needs immediate freshness, and use `revalidatePath` / `revalidateTag` to invalidate cache for subsequent visits.
