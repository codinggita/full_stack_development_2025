# 05. Server & Client Components

Next.js App Router uses **Server Components by default**. Client Components are used when a component needs browser-side interactivity or APIs.

Understanding the difference is important because **Server/Client Components and rendering strategies are different concepts**.

```text
Server / Client Components
        ↓
Where does the component code run?

Rendering
        ↓
How and when is the UI generated?
```

## Pages Router vs App Router

The Server/Client Component model is introduced with the **App Router**.

### Pages Router

The Pages Router does not use the React Server Components model. Its components are normal React components, and a page can be rendered on the server, in the browser, or both depending on the rendering approach.

For example, the Pages Router uses APIs such as:

```text
getServerSideProps()
getStaticProps()
getStaticPaths()
```

There is no `"use client"` boundary in the Pages Router.

### App Router

The App Router uses React Server Components:

```text
App Router
    ↓
Server Components by default
    ↓
"use client"
    ↓
Client Components when needed
```

A simple comparison:

| Pages Router                                                    | App Router                                   |
| --------------------------------------------------------------- | -------------------------------------------- |
| Normal React components                                         | Server Components by default                 |
| No React Server Components model                                | Supports Server and Client Components        |
| No `"use client"` directive                                     | Uses `"use client"` for Client Components    |
| Uses APIs such as `getServerSideProps()` and `getStaticProps()` | Uses the App Router data and rendering model |

> In the App Router, **Server Components and Client Components** refer to that routing model.

---

## 1. Server Components

Server Components are components that run on the server. In the App Router, components are **Server Components by default**.

```tsx
export default async function ProductsPage() {
	const products = await getProducts();

	return (
		<div>
			{products.map((product) => (
				<div key={product.id}>{product.name}</div>
			))}
		</div>
	);
}
```

Server Components are useful for fetching data, accessing server-side resources, and rendering content that does not need browser interaction.

### Server Component Restrictions

Server Components cannot use features that require the browser.

They cannot use client-side state, effects, event handlers, or browser APIs such as:

```text
useState
useEffect
onClick
onChange
window
document
localStorage
```

If a component needs these features, make that component a Client Component.

## 2. Client Components

Client Components are components that need client-side JavaScript and browser features. Add:

```tsx
"use client";
```

Example:

```tsx
"use client";

import { useState } from "react";

export default function Counter() {
	const [count, setCount] = useState(0);

	return <button onClick={() => setCount(count + 1)}>Count: {count}</button>;
}
```

Use Client Components for state, event handlers, effects, browser APIs, and client-side interaction.

### Client Component Restrictions

Client Components should not directly contain server-only resources or sensitive server logic.

For example, do not put database access directly inside a Client Component:

```tsx
"use client";

const users = await db.user.findMany();
```

Do not expose private database credentials, private API keys, or server credentials to client-side code.

A useful separation is:

```text
Server Component
    ↓
Server-only work
    ↓
Pass required data
    ↓
Client Component
    ↓
Interactive UI
```

## 3. `"use client"` vs `"use server"`

These two directives mark **different boundaries** — they are not opposites:

```text
"use client"  →  Client Component entry point (runs in the browser)
"use server"  →  Server Function / Server Action (runs on the server)
```

## `"use client"`

The `"use client"` directive creates a **Client Component** boundary. Any component in that file (and its imports in the client graph) can use state, effects, event handlers, and browser APIs.

```tsx
"use client";

export default function Button() {
	return <button onClick={() => alert("Hello")}>Click Me</button>;
}
```

Do not add `"use client"` to every component. Start with Server Components and add it only when client-side features are required.

## `"use server"`

The `"use server"` directive marks a **Server Action** — an async function that runs on the server and can be invoked from a form or Client Component (for example via `<form action={...}>` or `startTransition`).

```tsx
"use server";

export async function createProduct(formData: FormData) {
	const name = formData.get("name");
	// Server-side validation, database mutation, etc.
}
```

It can be placed at the top of a file (all exports become Server Actions) or inside a single function.

> **Important:** `"use client"` marks a **component** boundary; `"use server"` marks a **server function** boundary. You do not choose one instead of the other for the same piece of UI — they solve different problems.

## 4. Server/Client Component Boundaries

A Server Component can render a Client Component.

```tsx
// ProductPage.tsx
export default async function ProductPage() {
	const product = await getProduct();

	return (
		<div>
			<h1>{product.name}</h1>
			<AddToCartButton productId={product.id} />
		</div>
	);
}
```

```tsx
// AddToCartButton.tsx
"use client";

export default function AddToCartButton({ productId }: { productId: string }) {
	return <button onClick={() => addToCart(productId)}>Add to Cart</button>;
}
```

```text
Product Page
     │
     ├── Product information → Server Component
     └── Add to Cart         → Client Component
```

The entire page does not need to become a Client Component.

### Passing Data from Server to Client

Server Components can pass serializable data to Client Components through props.

```text
Server Component
       ↓
      Props
       ↓
Client Component
```

### Using `children`

A Client Component can receive server-rendered content through `children`:

```tsx
"use client";

export default function InteractivePanel({
	children,
}: {
	children: React.ReactNode;
}) {
	return (
		<div>
			<button>Toggle</button>
			{children}
		</div>
	);
}
```

A Server Component can use it:

```tsx
<InteractivePanel>
	<ProductDetails />
</InteractivePanel>
```

This allows server-side content and client-side interaction to work together.

## 5. Choosing Server vs Client Components

| If the component…                                      | Choose               |
| ------------------------------------------------------ | -------------------- |
| Needs state, event handlers, or browser APIs           | **Client Component** |
| Mainly fetches or displays data                        | **Server Component** |
| Needs server-only resources (DB, secrets, file system) | **Server Component** |

## 6. Best Practices

### Keep Client Components Small

Prefer a small Client Component instead of making an entire page a Client Component.

```text
Product Page → Server Component
   ├── Product information
   ├── Product description
   └── Add to Cart → Client Component
```

### Do Not Add `"use client"` Everywhere

Start with Server Components. Before adding the directive, ask:

```text
Does this component actually need client-side features?
```

If not, keep it as a Server Component.

### Do Not Fetch Initial Data with `useEffect`

Avoid making every data page a Client Component:

```tsx
"use client";

useEffect(() => {
	fetch("/api/products");
}, []);
```

If the data can be fetched on the server, use a Server Component instead.

### Do Not Put Secrets in Client Components

Never expose database passwords, private API keys, or secret tokens in client-side code. Use the `server-only` package for modules that must never reach the client bundle.

### Do Not Make the Whole Page Client-Side for One Button

If only one part needs interaction (e.g. Add to Cart), keep the page as a Server Component and isolate the interactive piece:

```text
Page → Server Component
   └── Interactive button → Client Component
```

## Summary

- App Router components are Server Components by default.
- Server Components run on the server and are useful for data fetching and server-side logic.
- Client Components are used when a component needs client-side interaction.
- `"use client"` creates a Client Component boundary; `"use server"` marks a Server Action (a server function, not a component).
- Client Components can use state, effects, event handlers, and browser APIs.
- Server Components cannot use client-side state, effects, event handlers, or browser APIs.
- Server Components can render Client Components.
- Server Components can pass serializable data to Client Components through props.
- Server-rendered content can be passed to Client Components through `children`.
- Keep Client Component boundaries as small as practical.
- Do not add `"use client"` to every component.
- Fetch initial data on the server — avoid `useEffect` + `fetch` when a Server Component can load the data.
- Never expose secrets in Client Components; use `server-only` for server-only modules.
- Start with Server Components and move only interactive or browser-dependent parts to Client Components.
- Server Components and rendering strategies are different concepts.

## Quick Decision Guide

```text
Does it need state?
    ↓
  Yes → Client Component

Does it need event handlers?
    ↓
  Yes → Client Component

Does it need browser APIs?
    ↓
  Yes → Client Component

Does it mainly fetch/display data?
    ↓
  Yes → Prefer Server Component

Does it need server-only resources?
    ↓
  Yes → Server Component
```

> **Simple rule:** Start with a Server Component. Move only the interactive or browser-dependent parts to Client Components.
