# 06. Server & Client Components

The Next.js App Router uses **React Server Components** to decide where components should run.

By default, components inside the `app/` directory are **Server Components**.

You can create a **Client Component** when a component needs browser-side features such as:

- State
- Event handlers
- Effects
- Browser APIs
- Interactive UI

The main idea is:

```text
Server Component
      ↓
Runs on the server

Client Component
      ↓
Runs on the client/browser
```

This allows a Next.js application to keep most of the application on the server while sending client-side JavaScript only where it is needed.

---

# 1. Server Components

A **Server Component** is a React component that runs on the server.

In the App Router, components are Server Components by default.

Example:

```tsx
export default function ProductsPage() {
	return (
		<div>
			<h1>Products</h1>
			<p>Product list</p>
		</div>
	);
}
```

No special directive is required.

```text
app/
└── products/
    └── page.tsx
```

The component is a Server Component by default.

---

# 2. Why Use Server Components?

Server Components are useful when the component does not need browser-side interactivity.

They allow you to:

- Fetch data on the server
- Access server-side resources
- Keep server-only logic away from the browser
- Reduce client-side JavaScript
- Render content on the server

For example:

```tsx
async function getProducts() {
	const response = await fetch("https://fakestoreapi.com/products");

	return response.json();
}

export default async function ProductsPage() {
	const products = await getProducts();

	return (
		<div>
			{products.map((product) => (
				<p key={product.id}>{product.title}</p>
			))}
		</div>
	);
}
```

The data fetching happens on the server.

---

# 3. Server Components Can Be Async

Server Components can be asynchronous.

Example:

```tsx
export default async function ProductsPage() {
	const response = await fetch("https://api.example.com/products");

	const products = await response.json();

	return (
		<div>
			{products.map((product) => (
				<p key={product.id}>{product.title}</p>
			))}
		</div>
	);
}
```

This is one of the useful features of the App Router.

You can fetch data directly inside a Server Component instead of moving the initial data fetching into:

```text
useEffect()
```

and then fetching it from the browser.

---

# 4. Server Component Restrictions

Server Components cannot use browser-only features.

For example, this is not valid as a Server Component:

```tsx
import { useState } from "react";

export default function Counter() {
	const [count, setCount] = useState(0);

	return <button>{count}</button>;
}
```

Why?

Because `useState()` requires client-side interactivity.

Similarly, Server Components cannot directly use browser APIs such as:

```text
window
document
localStorage
navigator
```

They also **cannot use client-side event handlers** such as:

```tsx
onClick;
onChange;
onSubmit;
```

Event handlers always require the component to run on the client — they are never valid in Server Components.

Example:

```tsx
export default function Button() {
	return <button onClick={() => alert("Hello")}>Click</button>;
}
```

This needs to be a Client Component.

---

# 5. Client Components

A **Client Component** is a component that can use client-side React features and browser APIs.

A Client Component is created by adding:

```tsx
"use client";
```

at the top of the file.

Example:

```tsx
"use client";

import { useState } from "react";

export default function Counter() {
	const [count, setCount] = useState(0);

	return <button onClick={() => setCount(count + 1)}>Count: {count}</button>;
}
```

The important part is:

```tsx
"use client";
```

It must appear before imports.

---

# 6. What Can Client Components Do?

Client Components can use features that require the browser.

Examples:

### State

```tsx
useState();
```

### Effects

```tsx
useEffect();
```

### Event Handlers

```tsx
onClick;
onChange;
onSubmit;
```

### Browser APIs

```text
window
document
localStorage
navigator
```

### Client-side Hooks

For example:

```tsx
useRouter();
usePathname();
useSearchParams();
```

These features are useful for interactive UI.

---

# 7. Example: Interactive Client Component

```tsx
"use client";

import { useState } from "react";

export default function LikeButton() {
	const [liked, setLiked] = useState(false);

	return (
		<button onClick={() => setLiked(!liked)}>
			{liked ? "Liked" : "Like"}
		</button>
	);
}
```

This component needs to run on the client because:

```text
User clicks button
       ↓
Event handler runs
       ↓
State changes
       ↓
UI updates
```

Therefore:

```tsx
"use client";
```

is required.

---

# 8. `"use client"` and `"use server"`

Two directives appear in Next.js App Router code. They serve different purposes and are **not opposites of each other**.

```text
"use client"  →  marks a Client Component boundary
"use server"  →  marks a Server Action (a server-side function, not a component)
```

### `"use client"`

`"use client"` marks a module as a **Client Component entry point**.

Example:

```tsx
"use client";

import { useState } from "react";
```

Once a file is marked with `"use client"`, its imports become part of the client-side component graph.

For example:

```text
Counter.tsx
   ↓
"use client"
   ↓
Button.tsx
   ↓
Icon.tsx
```

Components imported into the Client Component boundary are treated as part of that client-side module graph.

> Because of this, do not add `"use client"` to every component. Add it where client-side functionality is actually required.

### `"use server"`

`"use server"` marks a **Server Action** — an async function that runs on the server and can be called from Client Components (for example, from a form submission or button click).

Server Actions are covered in detail in **Phase 10**. For now, remember:

- `"use client"` creates a **component** boundary
- `"use server"` creates a **server function** boundary

They solve different problems and can appear in the same application.

---

# 9. Server vs Client Components

The simplest difference is:

```text
Server Component
    ↓
Server-side capabilities
    ↓
No browser-only interactivity

Client Component
    ↓
Browser-side capabilities
    ↓
State + Events + Effects + Browser APIs
```

### Comparison

| Server Component              | Client Component                |
| ----------------------------- | ------------------------------- |
| Default in App Router         | Requires `"use client"`         |
| Runs on the server            | Runs in the client/browser      |
| Can fetch data on the server  | Can fetch data from the browser |
| Can use server-only resources | Can use browser APIs            |
| Cannot use `useState`         | Can use `useState`              |
| Cannot use `useEffect`        | Can use `useEffect`             |
| Cannot handle client events   | Can handle client events        |
| Helps reduce client JS        | Adds client-side JS             |

---

# 10. Server/Client Component Boundaries

A **Server/Client Component boundary** is the point where Server Component code and Client Component code meet.

Consider:

```text
Server Component
       │
       ├── ProductList
       │
       └── AddToCartButton
                    ↓
              Client Component
```

The page can remain a Server Component while only the interactive button becomes a Client Component.

Example:

```tsx
// ProductPage.tsx

import AddToCartButton from "./AddToCartButton";

export default async function ProductPage() {
	const product = await getProduct();

	return (
		<div>
			<h1>{product.name}</h1>

			<p>{product.description}</p>

			<AddToCartButton productId={product.id} />
		</div>
	);
}
```

Client component:

```tsx
// AddToCartButton.tsx

"use client";

export default function AddToCartButton({ productId }: { productId: string }) {
	function handleClick() {
		console.log("Add product:", productId);
	}

	return <button onClick={handleClick}>Add to Cart</button>;
}
```

The architecture becomes:

```text
ProductPage
(Server Component)
      │
      ├── Product information
      │
      └── AddToCartButton
          (Client Component)
```

This is a common and recommended pattern.

---

# 11. Keep the Client Boundary Small

Suppose a page has:

```text
Product Page
├── Product Image
├── Product Details
├── Product Description
├── Reviews
└── Add to Cart Button
```

Only the button needs interactivity.

A good approach is:

```text
Product Page
(Server Component)
        │
        ├── Product Image
        ├── Product Details
        ├── Product Description
        ├── Reviews
        │
        └── Add to Cart Button
              ↓
         Client Component
```

Avoid making the entire page a Client Component just because one button needs `onClick`.

Instead of:

```tsx
"use client";

export default function ProductPage() {
	// Everything becomes part of the client component graph
}
```

prefer:

```text
Server Page
     ↓
Small Client Component
```

This can reduce the amount of JavaScript sent to the browser.

# 12. Third-Party Components and the `"use client"` Problem

A common real-world issue: you install a UI library (date picker, chart, carousel, etc.) that uses `useState` or other client features internally, but the library file does **not** include `"use client"`.

When you import it into a Server Component, Next.js throws an error because hooks and event handlers cannot run on the server.

**Solution:** wrap the third-party component in your own Client Component.

```tsx
// components/DatePickerWrapper.tsx

"use client";

import { DatePicker } from "some-ui-library";

export default function DatePickerWrapper(
	props: React.ComponentProps<typeof DatePicker>,
) {
	return <DatePicker {...props} />;
}
```

Then import the wrapper from your Server Component:

```tsx
// app/booking/page.tsx

import DatePickerWrapper from "@/components/DatePickerWrapper";

export default function BookingPage() {
	return (
		<div>
			<h1>Book a slot</h1>
			<DatePickerWrapper />
		</div>
	);
}
```

The wrapper creates the Client Component boundary. The Server Component page stays on the server; only the interactive widget is sent to the browser.

> Every student hits this when adding their first UI library. If you see errors about hooks or event handlers in a library import, wrap it — do not add `"use client"` to the library's source files inside `node_modules`.

# 13. Passing Data from Server to Client Components

Server Components can pass serializable data to Client Components through props.

Server Component:

```tsx
import AddToCartButton from "./AddToCartButton";

export default async function ProductPage() {
	const product = await getProduct();

	return (
		<div>
			<h1>{product.name}</h1>

			<AddToCartButton productId={product.id} />
		</div>
	);
}
```

Client Component:

```tsx
"use client";

export default function AddToCartButton({ productId }: { productId: string }) {
	return <button>Add {productId} to cart</button>;
}
```

The server obtains the data and passes the required value to the interactive component.

---

# 14. What Cannot Be Passed Directly?

Props passed from Server Components to Client Components need to be **serializable**.

Simple values are commonly suitable:

```text
string
number
boolean
null
arrays
plain objects
```

Example:

```tsx
<AddToCartButton productId='123' price={99} available={true} />
```

Avoid passing non-serializable values such as:

```text
functions
class instances
server-only objects
```

For example, this is not a normal Server → Client pattern:

```tsx
<ClientButton onClick={serverFunction} />
```

Instead, use appropriate Next.js server/client patterns such as Server Actions when a server-side operation needs to be triggered from client UI.

---

# 15. Client Components Can Import Other Client Components

A Client Component can import another Client Component.

Example:

```text
ProductPage
     ↓
ProductInteractive
     ↓
QuantitySelector
```

If the parent is already a Client Component:

```tsx
"use client";

import QuantitySelector from "./QuantitySelector";
```

the child can also participate in the client-side component tree.

---

# 16. Composing Server Content into Client Components via `children`

A common beginner misconception is:

> "If a Client Component imports a Server Component, the Server Component will automatically become a Client Component."

You **cannot** import a Server Component into a Client Component and expect it to stay server-side. The imported component becomes part of the client bundle.

Instead, Next.js supports passing Server Components to Client Components through **composition** — typically via the `children` prop.

Client Component:

```tsx
"use client";

export default function ClientLayout({
	children,
}: {
	children: React.ReactNode;
}) {
	return <section>{children}</section>;
}
```

Server Component:

```tsx
import ClientLayout from "./ClientLayout";

export default async function Page() {
	const data = await getData();

	return (
		<ClientLayout>
			<div>{data.title}</div>
		</ClientLayout>
	);
}
```

The server-rendered content is passed as `children` from the Server Component **into** the Client Component — not imported the other way around.

This pattern allows interactive client-side UI to wrap server-rendered content without turning all of that content into client-side code.

---

# 17. Client Component Restrictions & Server-Only Code

Client Components have access to browser functionality, but they should not directly use server-only resources.

For example, do not put secret server credentials in a Client Component:

```tsx
"use client";

const API_KEY = process.env.SECRET_API_KEY;
```

Anything that needs to remain secret should stay on the server.

Client Components should not directly access:

```text
Database
Private server files
Server-only secrets
Server-only Node.js APIs
```

For example, database access should normally happen in a Server Component or another server-side part of the application.

```text
Client Component → Server-side operation → Database   ✅

Client Component → Database                           ❌
```

Some code should never be included in the client bundle:

```text
Database credentials
Private API keys
Database queries
Internal server services
Secret environment variables
```

Keep this code on the server:

```tsx
async function getUser() {
	// Server-side database access
	return db.user.findFirst();
}
```

A Client Component should not import this server-only database logic directly.

A better structure is:

```text
Server Component
      ↓
getUser()
      ↓
Database
      ↓
Pass required data
      ↓
Client Component
```

To enforce this at build time, use the **`server-only`** npm package:

```tsx
import "server-only";

export async function getUser() {
	return db.user.findFirst();
}
```

If a Client Component accidentally imports a module marked with `server-only`, Next.js causes a **build error** — catching the mistake before it reaches production.

---

# 18. Environment Variables and Components

Environment variables without `NEXT_PUBLIC_` are intended for server-side use.

Example:

```env
DATABASE_URL=...
SECRET_API_KEY=...
```

These should remain on the server.

Variables prefixed with:

```text
NEXT_PUBLIC_
```

can be exposed to the browser.

Example:

```env
NEXT_PUBLIC_API_URL=https://api.example.com
```

Never use `NEXT_PUBLIC_` for secrets.

Therefore:

```text
SECRET_API_KEY       → Server only
NEXT_PUBLIC_API_URL  → Can be exposed to client
```

# 19. Common Pattern: Server Page + Client Interaction

A very common Next.js architecture is:

```text
Page
(Server Component)
      │
      ├── Fetch data
      ├── Render content
      │
      └── Interactive Component
              │
              ├── useState
              ├── Event handlers
              └── Browser APIs
```

Example:

```text
Product Page
│
├── Product Details       Server
├── Product Description   Server
├── Product Reviews       Server
│
└── Add to Cart           Client
```

This is often better than making the entire product page a Client Component.

# 20. Choosing Server vs Client Components

Use this simple decision process.

### Step 1: Does the component need interactivity?

For example:

```text
onClick
onChange
onSubmit
```

If yes → **Client Component**

---

### Step 2: Does it need React client-side state?

For example:

```text
useState
useReducer
```

If yes → **Client Component**

---

### Step 3: Does it need browser APIs?

For example:

```text
window
document
localStorage
navigator
```

If yes → **Client Component**

---

### Step 4: Does it need server-only functionality?

For example:

```text
Database
Private API key
Server-only service
```

If yes → **Server Component / server-side code**

---

### Step 5: Is it only displaying data?

If yes → **Prefer Server Component**

# 22. Common Mistakes

## Mistake 1: Adding `"use client"` Everywhere

Do not automatically add `"use client"` to every component.

Instead, ask:

```text
Does this component actually need client-side features?
```

If not, keep it as a Server Component.

---

## Mistake 2: Using `useEffect()` for Initial Server Data

A beginner may write:

```tsx
"use client";

useEffect(() => {
	fetch("/api/products");
}, []);
```

for every data-fetching page.

If the data can be fetched on the server, consider a Server Component instead.

---

## Mistake 3: Putting Secrets in Client Components

Never expose database passwords, private API keys, or secret tokens to client-side code.

Use the `server-only` package for modules that must never reach the client bundle.

---

## Mistake 4: Making a Whole Page Client-Side for One Button

Instead of:

```text
Entire Page → Client Component
```

prefer:

```text
Entire Page → Server Component
   └── Interactive Button → Client Component
```

---

## Mistake 5: Thinking Server Components Cannot Be Interactive

Server Components themselves cannot use client-side event handlers or state.

But a Server Component can include Client Components:

```text
Server Component → Client Component → Interactive UI
```

This allows a page to contain both server-rendered content and interactive client-side UI.

---

# 23. Recommended Architecture

For most applications, a good starting point is:

```text
Server Component
      │
      ├── Fetch data
      ├── Access server resources
      ├── Render content
      │
      └── Client Components
             │
             ├── Forms
             ├── Buttons
             ├── Modals
             ├── Dropdowns
             ├── Tabs
             └── Interactive widgets
```

Think of the server as handling:

```text
Data + Secrets + Server Logic
```

and the client as handling:

```text
Interaction + Browser APIs + Client State
```

# 24. Server vs Client Example

Consider an e-commerce product page:

```text
Product Page
│
├── Product Information    → Server Component
├── Product Description    → Server Component
├── Product Reviews        → Server Component
├── Quantity Selector      → Client Component
└── Add to Cart            → Client Component
```

The page does not need to become entirely client-side.

Only the parts that require client-side behavior need to be Client Components.

# Summary

- Components in the App Router are **Server Components by default**.
- Server Components run on the server and are useful for data fetching and server-side logic.
- Client Components are used for browser-side interactivity.
- `"use client"` marks a **Client Component** boundary; `"use server"` marks a **Server Action** (a server function, not a component). They are not opposites.
- Client Components can use state, effects, event handlers, and browser APIs.
- Server Components cannot use `useState`, `useEffect`, event handlers, or browser APIs — event handlers are **never** valid in Server Components.
- Server Components should be used for server-only resources such as databases and private secrets.
- Use the **`server-only`** package to cause a build error if server-only code is accidentally imported into a Client Component.
- Third-party UI libraries that use hooks internally often need a **wrapper Client Component** with `"use client"`.
- Server Components can pass serializable data to Client Components through props.
- Keep Client Component boundaries as small as practical.
- Pass server-rendered content into Client Components via **`children`**, not by importing Server Components into Client Components.
- Do not add `"use client"` to every component.
- Start with a Server Component; move only interactive or browser-dependent parts to Client Components.

## Quick Decision Guide

```text
Does the component need:

State?
  ↓ Yes → Client Component

Event handlers?
  ↓ Yes → Client Component

Browser APIs?
  ↓ Yes → Client Component

Server-only data/resources?
  ↓ Yes → Server Component

Only displaying/fetching data?
  ↓ Yes → Prefer Server Component
```

> **Simple rule:** Start with a Server Component. Move only the interactive or browser-dependent parts to Client Components.
