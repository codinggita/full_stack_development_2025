# 07. Rendering in Next.js

Rendering is the process of generating the UI that the browser displays.

In a web application, rendering can happen:

- In the **browser**
- On the **server**
- Ahead of time during the **build**
- Through a combination of these approaches

Next.js supports different rendering approaches so that each page can use the approach that best matches its data and user experience.

---

# 1. Rendering in Next.js

The main rendering concepts are:

```text
Rendering
│
├── Static Rendering
│   ├── SSG — Static Site Generation
│   └── ISR — Incremental Static Regeneration
│
├── Dynamic Rendering
│   └── Request-time rendering (SSR)
│
└── CSR — Client-Side Rendering
```

The important approaches are:

1. **CSR — Client-Side Rendering**
2. **SSR — Server-Side Rendering**
3. **SSG — Static Site Generation**
4. **ISR — Incremental Static Regeneration**

Next.js also uses the terms **Static Rendering** and **Dynamic Rendering** to describe how routes are rendered.

> **Important:** CSR, SSR, SSG, and ISR describe rendering approaches, while Static Rendering and Dynamic Rendering describe how Next.js generates a route. ISR is a **form of static rendering** with revalidation — not a separate top-level category.

---

## Static Rendering

**Static Rendering** means that a route is rendered ahead of the user's request and the generated result can be reused for multiple users.

The content does not need to be generated from scratch for every request.

Conceptually:

```text
Build / Static Generation
        ↓
Generate HTML
        ↓
Store / Cache Result
        ↓
User Request
        ↓
Serve Existing Result
```

Static rendering is useful when the content does not depend on request-specific information.

Examples:

```text
/about
/pricing
/docs
/blog/my-first-post
```

Static rendering usually provides:

- Fast responses
- Good scalability
- Good SEO for public content
- Reduced request-time server work

---

## Dynamic Rendering

**Dynamic Rendering** means that a route is rendered using request-specific information or data that must be determined at request time.

Conceptually:

```text
User Request
      ↓
Next.js Server
      ↓
Fetch / calculate request-specific data
      ↓
Generate response
      ↓
Browser
```

Dynamic rendering is useful when the output depends on information such as:

- Cookies
- Authentication
- Request-specific data
- User-specific information
- Frequently changing data that must be requested at runtime

Examples:

```text
/account
/orders
/profile
/personalized-dashboard
```

> Dynamic rendering is closely related to SSR because both involve generating the response at request time. In the App Router, Next.js commonly refers to this as **Dynamic Rendering**.

## What Triggers Dynamic Rendering in the App Router?

Next.js automatically treats a route as **dynamic** when the page uses request-specific APIs or opts out of caching.

Common triggers:

```text
cookies()            → triggers dynamic rendering
headers()            → triggers dynamic rendering
searchParams         → triggers dynamic rendering
cache: "no-store"    → triggers dynamic rendering
connection()         → triggers dynamic rendering
```

You can also force dynamic rendering explicitly:

```tsx
export const dynamic = "force-dynamic";
```

Example — reading cookies makes the route dynamic:

```tsx
import { cookies } from "next/headers";

export default async function ProfilePage() {
	const cookieStore = await cookies();
	const session = cookieStore.get("session");

	return <h1>Welcome, {session?.value}</h1>;
}
```

Because `cookies()` is used, Next.js cannot generate this page ahead of time for all users — it must render at request time.

To keep a route static, avoid request-specific APIs and use default static caching for data fetching.

# 2. NextJS Rendering strategies

## 1. CSR — Client-Side Rendering

**Client-Side Rendering (CSR)** means that the browser performs the main data fetching and UI updates after JavaScript has loaded.

For example:

```text
Browser
   ↓
Load JavaScript
   ↓
React runs
   ↓
Fetch API
   ↓
Update UI
```

A simple React example:

```tsx
"use client";

import { useEffect, useState } from "react";

export default function Products() {
	const [products, setProducts] = useState([]);

	useEffect(() => {
		fetch("https://fakestoreapi.com/products")
			.then((res) => res.json())
			.then(setProducts);
	}, []);

	return (
		<div>
			{products.map((product) => (
				<p key={product.id}>{product.title}</p>
			))}
		</div>
	);
}
```

Here, the browser fetches the products after the JavaScript code runs.

## CSR in the App Router

In the App Router, components are Server Components by default.

Therefore, a component using:

```tsx
useState();
useEffect();
```

needs to be a Client Component:

```tsx
"use client";
```

> **Important:** A Client Component is not automatically the same thing as a completely client-rendered page. Next.js can still pre-render Client Components and then hydrate them in the browser. CSR usually refers to data/UI work that happens in the browser after JavaScript loads.

## When to Use CSR

Reach for CSR when the **primary value of the page lives in the browser after load** — not when the page first arrives from the server.

Good fits:

| Situation                        | Why CSR works                                                                            |
| -------------------------------- | ---------------------------------------------------------------------------------------- |
| Highly interactive UI            | State updates, animations, and re-renders stay in the browser without a full page reload |
| Data depends on browser context  | Filters, sorting, pagination, or selections that change frequently on the client         |
| Real-time or user-driven updates | Chat, live dashboards, notifications, drag-and-drop                                      |
| Authenticated admin tools        | SEO rarely matters; interactivity and fast local feedback matter more                    |
| Content loaded after user action | Search-as-you-type, infinite scroll, tabbed panels that fetch on demand                  |

Typical examples:

```text
Chat application
Admin dashboard
Interactive analytics
Complex multi-step form
Client-side filtering / search
```

In the App Router, CSR usually means a **Client Component** that fetches with `useEffect`, `fetch`, or a client library (React Query, SWR) — not making the entire route a Client Component when a Server Component could fetch the initial data instead.

---

## 2. SSR — Server-Side Rendering

**Server-Side Rendering (SSR)** means that the server generates the HTML for a request before sending the response to the browser.

Conceptually:

```text
User Request
      ↓
Next.js Server
      ↓
Fetch request-specific data
      ↓
Generate HTML
      ↓
Browser
      ↓
Hydration for interactivity
```

SSR is useful when the content needs to be generated using information available at request time.

Examples:

```text
User profile
Personalized page
Authenticated dashboard
Order details
```

---

## SSR with the Pages Router

In the Pages Router, SSR is commonly implemented using:

```tsx
export async function getServerSideProps() {
	const response = await fetch("https://api.example.com/profile");
	const profile = await response.json();

	return {
		props: {
			profile,
		},
	};
}

export default function ProfilePage({ profile }) {
	return <h1>{profile.name}</h1>;
}
```

`getServerSideProps()` runs on the server for each request.

---

## SSR / Dynamic Rendering with the App Router

The App Router uses Server Components and server-side data access.

For example:

```tsx
async function getProfile() {
	const response = await fetch("https://api.example.com/profile", {
		cache: "no-store",
	});

	return response.json();
}

export default async function ProfilePage() {
	const profile = await getProfile();

	return <h1>{profile.name}</h1>;
}
```

Here, `cache: "no-store"` tells Next.js to fetch at request time, which triggers **dynamic rendering**.

> In modern Next.js, it is often more accurate to describe this App Router behavior as **Dynamic Rendering** rather than treating `SSR` as a separate API.

## When to Use SSR / Dynamic Rendering

Use SSR (Dynamic Rendering in the App Router) when the **response must reflect this specific request** — the output cannot be shared across users or pre-built at deploy time.

Good fits:

| Situation                         | Why server-side rendering fits                                             |
| --------------------------------- | -------------------------------------------------------------------------- |
| Authentication-gated pages        | Content depends on session cookies or tokens read on the server            |
| User-specific data                | Profile, orders, dashboard — each user sees different HTML                 |
| Request-time decisions            | Redirect unauthenticated users, show role-based layouts                    |
| Fresh data every visit            | Prices, inventory, or status that must not come from a shared static cache |
| SEO for personalized public pages | HTML includes real content in the first response, not a client fetch shell |

Typical examples:

```text
/account
/orders
/profile
/personalized-feed
/dashboard
```

In the App Router, this usually means a Server Component with `cache: "no-store"`, or APIs like `cookies()` / `headers()` / `searchParams` that force **dynamic rendering**.

---

## 3. SSG — Static Site Generation

**Static Site Generation (SSG)** means generating pages ahead of time so that the result can be served without generating the page for every request.

Conceptually:

```text
Build
  ↓
Fetch data
  ↓
Generate page
  ↓
Store / cache result
  ↓
Users receive the result
```

SSG is ideal when content can be generated ahead of time and does not need to change for every request.

Examples:

```text
/about
/pricing
/docs
/blog
```

---

## SSG with the Pages Router

In the Pages Router, SSG is commonly implemented using:

```tsx
export async function getStaticProps() {
	const response = await fetch("https://fakestoreapi.com/products");

	const products = await response.json();

	return {
		props: {
			products,
		},
	};
}

export default function StorePage({ products }) {
	return (
		<div>
			{products.map((product) => (
				<p key={product.id}>{product.title}</p>
			))}
		</div>
	);
}
```

`getStaticProps()` runs during the build process.

For dynamic routes, the Pages Router uses `getStaticPaths()` to define which paths to pre-render.

---

## Static Rendering in the App Router

In the App Router, static rendering can be achieved by using data that Next.js can cache and reuse.

Example:

```tsx
async function getProducts() {
	const response = await fetch("https://fakestoreapi.com/products", {
		cache: "force-cache",
	});

	return response.json();
}

export default async function StorePage() {
	const products = await getProducts();

	return (
		<div>
			{products.map((product) => (
				<p key={product.id}>{product.title}</p>
			))}
		</div>
	);
}
```

The important idea is:

```text
Generate once
     ↓
Reuse the result
```

> In the App Router, the term **Static Rendering** is commonly used for this behavior. SSG is the familiar term from the Pages Router.

## Static Generation for Dynamic Routes — `generateStaticParams`

For a dynamic route such as `/products/[id]`, Next.js needs to know **which IDs to pre-render at build time**.

Use `generateStaticParams`:

```tsx
// app/products/[id]/page.tsx

export async function generateStaticParams() {
	const response = await fetch("https://fakestoreapi.com/products");
	const products = await response.json();

	return products.map((product) => ({
		id: product.id.toString(),
	}));
}

export default async function ProductPage({
	params,
}: {
	params: Promise<{ id: string }>;
}) {
	const { id } = await params;

	const response = await fetch(`https://fakestoreapi.com/products/${id}`, {
		cache: "force-cache",
	});

	const product = await response.json();

	return <h1>{product.title}</h1>;
}
```

At build time, Next.js pre-renders pages such as:

```text
/products/1
/products/2
/products/3
```

Without `generateStaticParams`, a dynamic route may be rendered on demand instead of at build time.

Pair `generateStaticParams` with ISR when product data should update periodically without a full rebuild.

## When to Use SSG

Use SSG (Static Rendering in the App Router) when **the same HTML can be generated once and served to every user** — content does not depend on who is visiting or when they visit.

Good fits:

| Situation                         | Why static generation fits                                        |
| --------------------------------- | ----------------------------------------------------------------- |
| Rarely changing content           | About, pricing, legal pages — update only on deploy               |
| Public SEO pages                  | Full HTML available immediately; fast TTFB for crawlers and users |
| Shared catalog or docs            | One generated version serves all visitors                         |
| High traffic, stable data         | Build once, serve from cache at scale                             |
| Known dynamic paths at build time | Product or blog slugs pre-rendered via `generateStaticParams`     |

Typical examples:

```text
Marketing pages
Documentation
Blog posts
About page
Pricing page
/product/[id]  (with generateStaticParams)
```

In the App Router, this usually means a Server Component with default static caching or `cache: "force-cache"` on `fetch`.

---

## 4. ISR — Incremental Static Regeneration

**Incremental Static Regeneration (ISR)** extends static generation by allowing statically generated content to be updated after a period of time without rebuilding the entire application.

Conceptually:

```text
Generate Static Page
        ↓
Serve Cached Page
        ↓
Revalidation Time Reached
        ↓
Regenerate Page
        ↓
Serve Updated Version
```

For example, suppose:

```text
revalidate = 60 seconds
```

The page can be regenerated when the cached result becomes stale and the route is requested.

> ISR is a **form of static rendering** with controlled revalidation — not a separate rendering category from SSG.

---

## ISR with the Pages Router

In the Pages Router:

```tsx
export async function getStaticProps() {
	const response = await fetch("https://fakestoreapi.com/products");

	const products = await response.json();

	return {
		props: {
			products,
		},
		revalidate: 60,
	};
}

export default function StorePage({ products }) {
	return (
		<div>
			{products.map((product) => (
				<p key={product.id}>{product.title}</p>
			))}
		</div>
	);
}
```

Here, `revalidate: 60` means the generated result can be revalidated after 60 seconds.

---

## ISR with the App Router

In the App Router, a fetch request can specify a revalidation period:

```tsx
async function getProducts() {
	const response = await fetch("https://fakestoreapi.com/products", {
		next: {
			revalidate: 60,
		},
	});

	return response.json();
}

export default async function StorePage() {
	const products = await getProducts();

	return (
		<div>
			{products.map((product) => (
				<p key={product.id}>{product.title}</p>
			))}
		</div>
	);
}
```

For dynamic routes, combine `generateStaticParams` with `revalidate`:

```tsx
// app/products/[id]/page.tsx

export async function generateStaticParams() {
	const products = await fetch("https://fakestoreapi.com/products").then(
		(res) => res.json(),
	);

	return products.map((product) => ({
		id: product.id.toString(),
	}));
}

async function getProduct(id: string) {
	const response = await fetch(`https://fakestoreapi.com/products/${id}`, {
		next: { revalidate: 60 },
	});

	return response.json();
}

export default async function ProductPage({
	params,
}: {
	params: Promise<{ id: string }>;
}) {
	const { id } = await params;
	const product = await getProduct(id);

	return <h1>{product.title}</h1>;
}
```

## When to Use ISR

Use ISR when content **can be static most of the time** but should **refresh on a schedule** without redeploying the entire site.

Good fits:

| Situation                                    | Why ISR fits                                                         |
| -------------------------------------------- | -------------------------------------------------------------------- |
| Periodically updated catalogs                | Product listings, news feeds — stale for minutes/hours is acceptable |
| Content that changes often, not constantly   | Blog indexes, job boards, travel listings                            |
| Static performance with occasional freshness | Serve cached HTML fast; regenerate after `revalidate` interval       |
| Many pages, infrequent full rebuilds         | Update one route's cache instead of triggering a full build          |
| Dynamic routes with known IDs                | Combine `generateStaticParams` + `revalidate` for `/products/[id]`   |

Typical examples:

```text
Product catalog
News website
Blog listing
Real-estate listings
Travel listings
```

In the App Router, set `next: { revalidate: 60 }` on `fetch`, or use route-level `export const revalidate = 60`. For updates triggered by an admin action, use on-demand revalidation (Caching & Revalidation).

## Time-Based vs On-Demand Revalidation

Time-based revalidation refreshes content after a set interval.

ISR also supports **on-demand revalidation** when content changes immediately — for example, after an admin updates a product:

```text
revalidatePath("/products")
revalidateTag("products", "max")
```

On-demand revalidation is covered in detail in **Caching & Revalidation**. For fetch cache options (`force-cache`, `revalidate`, `no-store`), see that topic — here the focus is how those choices affect rendering strategy.

# 3. Rendering Strategies Compared

## Static Rendering vs Dynamic Rendering

| Static Rendering                    | Dynamic Rendering                                                                |
| ----------------------------------- | -------------------------------------------------------------------------------- |
| Generated ahead of request          | Generated at request time                                                        |
| Result can be reused                | Result depends on request                                                        |
| Very fast for repeated requests     | Useful for personalized data                                                     |
| Good for public content             | Good for user-specific content                                                   |
| Example: `/about`                   | Example: `/account`                                                              |
| Triggered by default static caching | Triggered by `cookies()`, `headers()`, `searchParams`, `cache: "no-store"`, etc. |

## CSR vs SSR vs SSG vs ISR

| Strategy | Where main rendering/data work happens | When              | Best for                          |
| -------- | -------------------------------------- | ----------------- | --------------------------------- |
| CSR      | Browser                                | After JS loads    | Highly interactive UI             |
| SSR      | Server                                 | Every request     | Request-specific content          |
| SSG      | Build/static generation                | Ahead of requests | Mostly static content             |
| ISR      | Static generation + revalidation       | Periodically      | Content that changes occasionally |

A simple way to remember:

```text
CSR  → Browser renders / fetches
SSR  → Server renders for request
SSG  → Generate ahead of time
ISR  → Generate ahead of time + update periodically
```

# 4. Choosing the Rendering Strategy

Ask these questions when deciding how a page should render.

## Question 1: Can the content be generated ahead of time?

```text
YES
 ↓
Static Rendering / SSG
```

Examples:

```text
/about
/pricing
/docs
```

---

## Question 2: Can it be generated ahead of time but needs periodic updates?

```text
YES
 ↓
ISR
```

Examples:

```text
/products
/news
/blog
```

---

## Question 3: Does it depend on request-specific information?

```text
YES
 ↓
Dynamic Rendering / SSR
```

Examples:

```text
/account
/orders
/profile
```

---

## Question 4: Is the page mainly a highly interactive browser application?

```text
YES
 ↓
CSR / Client-side data fetching
```

Examples:

```text
/chat
/interactive-dashboard
/analytics
```

# 5. A Real-World Example

An e-commerce application can use multiple rendering approaches.

```text
/about
    ↓
Static Rendering / SSG

/products
    ↓
ISR

/products/123
    ↓
ISR (with generateStaticParams)

/account
    ↓
Dynamic Rendering / SSR

/cart
    ↓
Client-side interactivity / CSR
```

The important point is:

> A Next.js application does not need to use one rendering strategy for the entire application.

Different routes can use different approaches based on their requirements.

# 6. Rendering and SEO

Rendering strategy can affect how quickly important page content becomes available in the initial response.

Static and server-rendered pages can provide HTML content before client-side JavaScript finishes loading, which is useful for public, SEO-focused pages.

However:

> Rendering strategy alone does not guarantee good SEO.

Good SEO also depends on:

- Metadata
- Page content
- Semantic HTML
- Internal links
- Structured data when appropriate
- Site performance
- Accessibility

For public content-heavy pages, static rendering, ISR, or dynamic rendering can all be suitable depending on how frequently the content changes.

---

# 7. Rendering and Performance

Different strategies have different performance characteristics.

### CSR

```text
JavaScript → Fetch data → Render UI
```

The initial experience can depend heavily on JavaScript and client-side data fetching.

### SSR / Dynamic Rendering

```text
Request → Server generates response → Browser receives HTML
```

The server performs work for the request, but the browser can receive meaningful HTML earlier.

### SSG / Static Rendering

```text
Generate ahead of time → Serve existing result
```

This can be extremely fast because the same generated result can be reused.

### ISR

```text
Static result + periodic revalidation
```

ISR provides static delivery while allowing content to become updated over time.

# 8. Common Mistakes

## Mistake 1: Thinking Client Component = CSR

This is not always true.

```tsx
"use client";
```

means the component is a **Client Component**.

It does not automatically mean the entire page is rendered only in the browser.

Next.js can pre-render Client Components and then hydrate them.

---

## Mistake 2: Using CSR for Everything

Not every page needs:

```tsx
"use client";
useEffect();
fetch();
```

For data that can be fetched on the server, a Server Component can often be simpler:

```tsx
export default async function ProductsPage() {
	const response = await fetch("https://api.example.com/products");

	const products = await response.json();

	return <div>...</div>;
}
```

Use Client Components when browser-side interactivity or client-only APIs are actually required.

---

## Mistake 3: Using SSR for Everything

SSR is useful for request-specific content, but not every page needs request-time rendering.

If content can be generated and reused, static rendering may be a better choice.

---

## Mistake 4: Using SSG for Frequently Changing Data

If data changes constantly, rebuilding the application for every change is not practical.

Consider ISR or dynamic rendering depending on the freshness requirements.

---

## Mistake 5: Thinking ISR Means Real-Time Data

ISR does not mean that every request gets the newest data immediately.

It uses cached/static results and revalidation.

If data must always be generated from the current request, dynamic rendering may be more appropriate.

---

## Mistake 6: Not Knowing Why a Page Became Dynamic

If a page unexpectedly renders at request time, check whether it uses:

```text
cookies()
headers()
searchParams
cache: "no-store"
```

Remove or isolate request-specific APIs when static rendering is intended.

---

# Summary

- **Rendering** determines when and where page content is generated.
- **Static Rendering** includes **SSG** and **ISR** — both generate ahead of time; ISR adds revalidation.
- **Dynamic Rendering** generates at request time (closely related to SSR).
- **CSR** performs important rendering/data work in the browser.
- Dynamic rendering is triggered by `cookies()`, `headers()`, `searchParams`, `cache: "no-store"`, and similar APIs.
- Use **`generateStaticParams`** to pre-render dynamic routes such as `/products/[id]` at build time.
- ISR supports **time-based** revalidation (`revalidate: 60`) and **on-demand** revalidation (`revalidatePath`, `revalidateTag`) — covered in **Caching & Revalidation**.
- A single Next.js application can use multiple rendering approaches.
- A Client Component is **not automatically the same thing as CSR**.

### Quick Decision Guide

```text
Can generate ahead of time?
        │
        ├── Yes → Does it need periodic updates?
        │             │
        │             ├── No → SSG / Static Rendering
        │             │
        │             └── Yes → ISR
        │
        └── No → Does it depend on request/user data?
                      │
                      ├── Yes → SSR / Dynamic Rendering
                      │
                      └── No → Consider CSR / client-side data fetching
```

> **Simple rule:** Prefer static rendering when content can be reused, ISR when it needs periodic updates, dynamic rendering when it depends on the request, and client-side rendering/data fetching when the browser needs to control the interaction or data flow.
