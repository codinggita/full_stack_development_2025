# 04. Layouts

Layouts are one of the important features of the **Next.js App Router**.

A layout allows you to create UI that is shared between multiple pages and remains mounted while users move between routes.

For example, a typical application may have:

```text
┌─────────────────────────────┐
│           Header            │
├─────────────────────────────┤
│                             │
│         Page Content        │
│                             │
├─────────────────────────────┤
│           Footer            │
└─────────────────────────────┘
```

Instead of writing the header and footer in every page, they can be placed inside a layout.

---

# 1. What is a Layout?

A **layout** is a special Next.js file named:

```text
layout.tsx
```

It is used to define UI that is shared by the pages inside that route segment.

Example:

```text
app/
├── layout.tsx
├── page.tsx
└── about/
    └── page.tsx
```

The root layout can contain:

```text
Header
    ↓
Page content
    ↓
Footer
```

Both `/` and `/about` can use the same layout.

A `page.tsx` file represents the UI for a specific route. A `layout.tsx` file provides shared UI around pages in its route segment.

```text
page.tsx   → page-specific UI
layout.tsx → shared UI
```

---

# 2. Root Layout

The **Root Layout** is the top-level layout of an App Router application.

It is located at:

```text
app/layout.tsx
```

It must define:

```tsx
<html>
<body>
```

Example:

```tsx
import "./globals.css";

export default function RootLayout({
	children,
}: {
	children: React.ReactNode;
}) {
	return (
		<html lang='en'>
			<body>{children}</body>
		</html>
	);
}
```

Here, `{children}` represents the page or nested layout being rendered inside the current layout.

```text
Root Layout
    │
    ├── Header
    │
    ├── {children}
    │
    └── Footer
```

The root layout is also a common place for:

- Global CSS
- Global providers
- Common application UI
- Metadata

Wrap `{children}` with providers here when needed — for example, an auth session provider or a theme provider.

> Layouts are **Server Components by default**. You cannot use `useState`, `useEffect`, or other client hooks directly inside a layout. If a layout needs interactivity, extract that part into a separate Client Component and import it into the layout.

> The root layout is different from an ordinary component because Next.js treats `layout.tsx` as a special file convention.

---

# 3. Example: Shared UI in a Layout

Project structure:

```text
app/
├── layout.tsx
├── page.tsx
├── products/
│   └── page.tsx
└── about/
    └── page.tsx
```

Root layout:

```tsx
import Navbar from "@/components/Navbar";
import Footer from "@/components/Footer";

export default function RootLayout({
	children,
}: {
	children: React.ReactNode;
}) {
	return (
		<html lang='en'>
			<body>
				<Navbar />

				<main>{children}</main>

				<Footer />
			</body>
		</html>
	);
}
```

Now:

```text
/            → Home
/products    → Products
/about       → About
```

all share the same layout. Each page only defines its own content; the shared UI lives in the layout.

Reusable UI such as `Navbar` and `Footer` normally live in `components/` and are imported into the layout.

---

# 4. Nested Layouts

Layouts can be nested.

```text
Root Layout
      ↓
Section Layout
      ↓
Page
```

Example:

```text
app/
├── layout.tsx
├── page.tsx
│
└── dashboard/
    ├── layout.tsx
    ├── page.tsx
    └── settings/
        └── page.tsx
```

Here:

```text
Root Layout
    ↓
Dashboard Layout
    ↓
Dashboard Page
```

Root layout:

```tsx
export default function RootLayout({
	children,
}: {
	children: React.ReactNode;
}) {
	return (
		<html lang='en'>
			<body>
				<header>Website Header</header>

				{children}

				<footer>Website Footer</footer>
			</body>
		</html>
	);
}
```

Dashboard layout:

```tsx
export default function DashboardLayout({
	children,
}: {
	children: React.ReactNode;
}) {
	return (
		<section>
			<aside>Dashboard Menu</aside>

			<main>{children}</main>
		</section>
	);
}
```

Dashboard page:

```tsx
export default function DashboardPage() {
	return <h1>Dashboard</h1>;
}
```

The resulting structure is:

```text
Website Header
      ↓
Dashboard Menu
      ↓
Dashboard
      ↓
Website Footer
```

The dashboard layout can contain UI specific to the dashboard section.

---

# 5. Layout Hierarchy

Consider:

```text
app/
├── layout.tsx
└── dashboard/
    ├── layout.tsx
    └── settings/
        ├── layout.tsx
        └── page.tsx
```

The page is rendered inside the layout hierarchy:

```text
Root Layout
    │
    └── Dashboard Layout
            │
            └── Settings Layout
                    │
                    └── Settings Page
```

This allows each section to add its own shared UI.

---

# 6. Layout Persistence

One of the important advantages of layouts is that they **persist across route changes within their route segment**.

For example:

```text
/dashboard
/dashboard/settings
/dashboard/profile
```

can share:

```text
Dashboard Layout
```

When moving between these pages, the shared dashboard layout remains mounted while the page content changes.

Conceptually:

```text
Dashboard Layout
┌─────────────────────────────┐
│ Sidebar                     │
│                             │
│ ┌─────────────────────────┐ │
│ │ Page Content             │ │
│ │                          │ │
│ └─────────────────────────┘ │
└─────────────────────────────┘
```

Route change:

```text
/dashboard
       ↓
/dashboard/settings
```

The layout remains:

```text
Dashboard Layout
       ↓
New Page Content
```

This is useful for UI such as:

- Sidebars
- Section menus
- Headers
- Persistent controls
- Dashboard shells

---

# 7. Layout vs Template

Next.js also supports a special file called:

```text
template.tsx
```

Both wrap pages, but they behave differently:

```text
layout.tsx   → persists, stays mounted across navigation
template.tsx → re-mounts on every navigation (fresh instance each time)
```

Use a **layout** when shared UI should remain mounted — for example, a sidebar or site header.

Use a **template** when you need a fresh instance on each navigation — for example:

- Page enter/exit animations
- Per-page analytics tracking
- Resetting local state when the route changes

Example:

```text
app/
├── layout.tsx
├── template.tsx
└── dashboard/
    └── page.tsx
```

The key difference is **persistence vs re-mounting**.

# 8. Multiple Layouts

A large application may have different layouts for different sections.

For example:

```text
Marketing Website  → Marketing Layout
Dashboard          → Dashboard Layout
Admin Panel        → Admin Layout
```

A project can organize these sections using route groups.

Example:

```text
app/
├── layout.tsx
│
├── (marketing)/
│   ├── layout.tsx
│   ├── page.tsx
│   └── pricing/
│       └── page.tsx
│
└── (dashboard)/
    ├── layout.tsx
    └── dashboard/
        ├── page.tsx
        └── settings/
            └── page.tsx
```

The route group names:

```text
(marketing)
(dashboard)
```

do not appear in the URL.

This allows different parts of an application to have different shared UI.

# 9. Complete Layout Example

A small application can be organized like this:

```text
app/
├── layout.tsx
├── page.tsx
│
├── products/
│   ├── page.tsx
│   └── [id]/
│       └── page.tsx
│
└── dashboard/
    ├── layout.tsx
    ├── page.tsx
    └── settings/
        └── page.tsx

components/
├── Navbar.tsx
└── Footer.tsx
```

The layout hierarchy:

```text
Root Layout
│
├── Home
│
├── Products
│   └── Product Details
│
└── Dashboard Layout
    ├── Dashboard
    └── Settings
```

Each route uses the appropriate layouts while page content changes inside `{children}`.

# 10. Recommended Layout Organization

A practical structure for a medium-sized application:

```text
src/
├── app/
│   ├── layout.tsx
│   ├── page.tsx
│   │
│   ├── products/
│   │   └── page.tsx
│   │
│   └── dashboard/
│       ├── layout.tsx
│       ├── page.tsx
│       └── settings/
│           └── page.tsx
│
└── components/
    ├── Navbar.tsx
    └── Footer.tsx
```

A good rule is:

```text
Application-wide shared UI  → Root Layout
Section-specific shared UI → Nested Layout
Reusable UI component      → components/
```

# 11. Layout Best Practices

## 1. Keep Global UI in the Root Layout

Examples: site header, footer, global providers, global CSS.

## 2. Keep Section UI in Nested Layouts

Example: a dashboard sidebar belongs in `dashboard/layout.tsx`, not repeated on every dashboard page.

## 3. Do Not Put Page-Specific UI in a Layout

If a UI element is needed only by `/products`, it belongs in `products/page.tsx`.

## 4. Avoid Unnecessary Layouts

Create a nested layout only when multiple routes need the same shared UI.

## 5. Extract Interactive Parts into Client Components

Layouts are Server Components by default. Import Client Components when a shared UI element needs hooks or browser interactivity.

## 6. Use Components for Reusable Shared UI

Keep layout files focused on structure. Move reusable pieces such as `Navbar` and `Footer` into `components/`.

---

# Summary

- A `layout.tsx` file provides shared UI for a route segment.
- `app/layout.tsx` is the root layout and must define `<html>` and `<body>`.
- Layouts are Server Components by default — use Client Components for interactivity.
- Layouts can be nested for section-specific shared UI.
- Layouts persist across route changes within their route segment.
- `template.tsx` re-mounts on each navigation; `layout.tsx` persists.
- Route groups organize sections with different layouts without adding group names to URLs.
- Wrap `{children}` with global providers in the root layout when needed.
- Keep global UI in the root layout and section-specific UI in nested layouts.

> **Simple rule:** Put application-wide shared UI in the root layout, section-specific shared UI in nested layouts, and page-specific UI inside pages.
