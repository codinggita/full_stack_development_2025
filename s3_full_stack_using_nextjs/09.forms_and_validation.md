# 09. Forms & Validation

Forms are an important part of most web applications.

Users use forms to:

- Log in
- Create an account
- Update their profile
- Create products
- Submit feedback
- Search for information
- Change application settings

A form usually follows this flow:

```text
User enters data
      ↓
Form validation
      ↓
Valid?
   /      \
 No        Yes
 ↓          ↓
Show       Submit
errors       ↓
          Server
             ↓
        Process data
```

Next.js applications can handle forms using both Client Components and Server-side logic.

---

# 1. Forms in Next.js

A form in Next.js uses normal HTML form elements:

```html
<form>
  <input />
  <button />
</form>
```

Example:

```tsx
export default function LoginForm() {
  return (
    <form>
      <label>
        Email
        <input
          type="email"
          name="email"
        />
      </label>

      <label>
        Password
        <input
          type="password"
          name="password"
        />
      </label>

      <button type="submit">
        Login
      </button>
    </form>
  );
}
```

The important HTML elements are:

```text
<form>
<input>
<select>
<textarea>
<button>
<label>
```

Every input that should be submitted needs a **`name` attribute** — without it, the field's value is not included when the form is submitted:

```tsx
<input type="email" name="email" />
```

Next.js does not replace normal HTML forms. It provides additional patterns for handling form submissions and server-side processing.

---

# 2. Form Handling

**Form handling** means receiving the values entered by the user and processing them.

A traditional form submission looks like:

```text
User
 ↓
Fill form
 ↓
Submit
 ↓
Server receives data
 ↓
Validate
 ↓
Process
```

In Next.js, form handling can be done using:

- Normal form submission
- Client-side event handling
- Server Actions

For modern App Router applications, Server Actions provide a convenient way to execute server-side logic from a form.

---

# 3. Submitting to a Server Action

In the App Router, a form can submit directly to a **Server Action** — a server-side function passed to the form's `action` prop:

```tsx
import { createUser } from "./actions";

export default function SignupForm() {
  return (
    <form action={createUser}>
      <input type="email" name="email" />
      <input type="password" name="password" />
      <button type="submit">Create Account</button>
    </form>
  );
}
```

When the user submits, Next.js sends the form data to `createUser` on the server.

The Server Action itself — the `"use server"` directive, reading `FormData`, validation, mutations, revalidation, and returning errors — is covered in **Server Actions**.

---

# 4. Form Validation

Validation means checking whether submitted data follows the application's rules.

For example, a signup form may require:

```text
Email → Required and valid email
Password → Required and minimum 8 characters
Name → Required
```

Validation flow:

```text
Form Data
    ↓
Validate
    ↓
Valid?
 /    \
No     Yes
↓       ↓
Errors  Continue
```

Validation should happen on the server even when client-side validation is also used.

> Client-side validation improves user experience. Server-side validation protects the application.

---

# 5. Client-Side Validation

Client-side validation happens in the browser before the form is sent to the server.

Example:

```tsx
"use client";

import { useState } from "react";

export default function SignupForm() {
  const [email, setEmail] = useState("");
  const [error, setError] = useState("");

  function handleSubmit(
    event: React.FormEvent<HTMLFormElement>
  ) {
    event.preventDefault();

    if (!email) {
      setError("Email is required");
      return;
    }

    setError("");
  }

  return (
    <form onSubmit={handleSubmit}>
      <input
        type="email"
        value={email}
        onChange={(event) =>
          setEmail(event.target.value)
        }
      />

      {error && <p>{error}</p>}

      <button type="submit">
        Submit
      </button>
    </form>
  );
}
```

The browser checks the input before sending it to the server.

---

# 6. Advantages of Client-Side Validation

Client-side validation provides fast feedback.

For example:

```text
User enters invalid email
        ↓
Browser immediately shows:
"Enter a valid email"
```

Advantages:

- Immediate feedback
- Better user experience
- Fewer unnecessary requests
- Easier interactive validation

However, client-side validation should **not** be treated as a security boundary.

A user can bypass browser validation and send a request directly to the server.

---

# 7. Server-Side Validation

Server-side validation happens on the server after form data is submitted. The server is the **trusted validation boundary** — client-side checks can always be bypassed.

The server should validate every field before:

```text
Database insertion
Authentication
Business logic
External API requests
```

How to implement server-side validation inside a Server Action — including reading submitted data, returning `{ error }` or `{ errors: { ... } }`, and displaying those errors in the UI — is covered in **Server Actions**.

---

# 8. Why Server-Side Validation Is Required

Never rely only on:

```text
Client-side validation
```

because the client can be bypassed.

For example:

```text
Browser
   ↓
Client validation
   ↓
Server
```

A user can instead send:

```text
Custom HTTP request
   ↓
Server
```

Therefore:

```text
Client-side validation
        +
Server-side validation
        ↓
Better UX + Server protection
```

---

# 9. Client-Side vs Server-Side Validation

| Client-Side Validation | Server-Side Validation |
|---|---|
| Runs in browser | Runs on server |
| Fast feedback | Trusted validation boundary |
| Improves UX | Protects server and data |
| Can be bypassed | Cannot be skipped by the client |
| Not enough by itself | Always required for submitted data |

Simple rule:

```text
Client validation
    ↓
Better user experience

Server validation
    ↓
Required for security and correctness
```

# 10. Using HTML Validation

HTML already provides basic validation.

Example:

```tsx
<input
  type="email"
  name="email"
  required
/>
```

Other useful attributes include:

```text
required
minLength
maxLength
min
max
pattern
type
```

Example:

```tsx
<input
  type="password"
  name="password"
  required
  minLength={8}
/>
```

This gives the browser basic validation before submission.

However, server-side validation is still required.

# 11. Form Errors

Forms should clearly show validation errors.

Bad experience:

```text
Form submission failed.
```

Better experience:

```text
Email
[invalid-email]

Please enter a valid email address.
```

Errors should ideally be shown near the field that caused the problem.

Example:

```tsx
<label htmlFor="email">
  Email
</label>

<input
  id="email"
  name="email"
  type="email"
/>

<p>
  Please enter a valid email address.
</p>
```

---

# 12. Server Validation Errors

When validation fails on the server, returning a **structured error object** makes it much easier to show useful feedback in the form UI.

A single generic message:

```text
Something went wrong.
```

is harder to act on than field-level errors:

```text
{
  errors: {
    email: "Please enter a valid email address.",
    password: "Password must be at least 8 characters.",
  }
}
```

Field-level errors let you show each message beside the input that caused it — the same pattern used for client-side validation in **Form Errors** and **React Hook Form + Server Actions**.

How the server returns these errors from a Server Action, and how the Client Component receives them with `useActionState`, is covered in **Server Actions**.

---

# 13. Form Submission States

A form should communicate what is happening after submission.

For example:

```text
Before submission:
[Create Account]

During submission:
[Creating Account...]

After success:
Account created
```

The user should know when the form is being processed.

Without a submission state:

```text
Click Submit
    ↓
Nothing changes
    ↓
User clicks again
    ↓
Duplicate request
```

A submission state helps prevent confusion and accidental repeated submissions.

---

# 14. `useFormStatus`

React provides `useFormStatus()` for reading the status of a parent form submission.

Example:

```tsx
"use client";

import { useFormStatus } from "react-dom";

export function SubmitButton() {
  const { pending } = useFormStatus();

  return (
    <button type="submit" disabled={pending}>
      {pending ? "Creating..." : "Create Account"}
    </button>
  );
}
```

Use it inside the form:

```tsx
<form action={createUser}>
  <input
    name="email"
    type="email"
  />

  <SubmitButton />
</form>
```

The flow is:

```text
Submit form
    ↓
pending = true
    ↓
Show "Creating..."
    ↓
Server Action completes
    ↓
pending = false
```

# 15. Zod

**Zod** is a TypeScript-first schema validation library.

It allows you to define the expected structure of form data.

Example:

```tsx
import { z } from "zod";

const signupSchema = z.object({
  email: z.email(),
  password: z.string().min(8),
});
```

The schema describes the rules:

```text
email
  ↓
Must be a valid email

password
  ↓
Must contain at least 8 characters
```

You can then validate submitted data against the schema.

> These examples use **Zod v4** syntax (`z.email()`). In Zod v3, use `z.string().email()` instead — the chained form still works but is deprecated in v4.

---

# 16. Zod Validation Example

Example:

```tsx
import { z } from "zod";

const signupSchema = z.object({
  email: z.email(),
  password: z.string().min(8),
});

const result = signupSchema.safeParse({
  email: "user@example.com",
  password: "password123",
});

if (!result.success) {
  console.log(result.error);
}
```

`safeParse()` does not throw an exception for invalid input.

Instead, it returns:

```text
success = true
```

or:

```text
success = false
```

This is useful for form validation.

---

# 17. Zod with Server Actions

The same Zod schema from client-side validation can be reused on the server to validate submitted form data inside a Server Action.

Using a schema with `safeParse()` inside a Server Action, returning structured field errors, and wiring those errors back to the form UI — is covered in **Server Actions**.

---

# 18. Why Use Zod?

Without a validation library, you may write many manual checks:

```tsx
if (!email) {
  // ...
}

if (!email.includes("@")) {
  // ...
}

if (password.length < 8) {
  // ...
}
```

With Zod, the rules are defined in one schema:

```tsx
const schema = z.object({
  email: z.email(),
  password: z.string().min(8),
});
```

Benefits include:

- Centralized validation rules
- Reusable schemas
- TypeScript integration
- Structured validation errors
- Less repetitive validation code

# 19. React Hook Form

**React Hook Form** is a library for managing forms in React.

It helps with:

- Form state
- Field registration
- Validation
- Submission handling
- Form errors
- Performance

Example:

```tsx
"use client";

import { useForm } from "react-hook-form";

type LoginFormValues = {
  email: string;
  password: string;
};

export default function LoginForm() {
  const {
    register,
    handleSubmit,
    formState: { errors },
  } = useForm<LoginFormValues>();

  function onSubmit(data: LoginFormValues) {
    console.log(data);
  }

  return (
    <form onSubmit={handleSubmit(onSubmit)}>
      <input
        type="email"
        {...register("email", {
          required: "Email is required",
        })}
      />

      {errors.email && (
        <p>{errors.email.message}</p>
      )}

      <input
        type="password"
        {...register("password", {
          required: "Password is required",
        })}
      />

      {errors.password && (
        <p>{errors.password.message}</p>
      )}

      <button type="submit">
        Login
      </button>
    </form>
  );
}
```

---

# 20. React Hook Form + Zod

React Hook Form and Zod solve different problems.

```text
React Hook Form
       ↓
Manage form state and submission

Zod
       ↓
Validate data against a schema
```

They can be combined.

The common integration uses:

```text
React Hook Form
       +
Zod
       ↓
Form management + schema validation
```

Example:

```tsx
"use client";

import { useForm } from "react-hook-form";
import { zodResolver } from "@hookform/resolvers/zod";
import { z } from "zod";

const schema = z.object({
  email: z.email(),
  password: z.string().min(8),
});

type LoginFormValues = z.infer<typeof schema>;

export default function LoginForm() {
  const {
    register,
    handleSubmit,
    formState: { errors },
  } = useForm<LoginFormValues>({
    resolver: zodResolver(schema),
  });

  function onSubmit(data: LoginFormValues) {
    console.log(data);
  }

  return (
    <form onSubmit={handleSubmit(onSubmit)}>
      <label htmlFor="email">
        Email
      </label>

      <input
        id="email"
        type="email"
        {...register("email")}
      />

      {errors.email && (
        <p>{errors.email.message}</p>
      )}

      <label htmlFor="password">
        Password
      </label>

      <input
        id="password"
        type="password"
        {...register("password")}
      />

      {errors.password && (
        <p>{errors.password.message}</p>
      )}

      <button type="submit">
        Login
      </button>
    </form>
  );
}
```

# 21. React Hook Form + Server Actions

Client-side validation with React Hook Form does not replace server-side validation. For production forms — such as BuildMart admin pages — you typically use **both**:

```text
React Hook Form + Zod  →  client-side feedback
        ↓
Server Action + Zod    →  trusted server validation (Server Actions)
```

### Client-side pattern

Use React Hook Form with a Zod resolver for immediate field-level errors:

```tsx
"use client";

import { useForm } from "react-hook-form";
import { zodResolver } from "@hookform/resolvers/zod";
import { z } from "zod";

const schema = z.object({
  name: z.string().min(1, "Name is required"),
  price: z.coerce.number().min(0, "Price must be positive"),
});

type FormValues = z.infer<typeof schema>;

export default function ProductForm() {
  const {
    register,
    handleSubmit,
    formState: { errors },
  } = useForm<FormValues>({
    resolver: zodResolver(schema),
  });

  function onSubmit(data: FormValues) {
    // Wire to Server Action — see Server Actions
    console.log(data);
  }

  return (
    <form onSubmit={handleSubmit(onSubmit)} noValidate>
      <label htmlFor="name">Name</label>
      <input id="name" {...register("name")} />
      {errors.name && <p role="alert">{errors.name.message}</p>}

      <label htmlFor="price">Price</label>
      <input id="price" type="number" {...register("price")} />
      {errors.price && <p role="alert">{errors.price.message}</p>}

      <button type="submit">Save</button>
    </form>
  );
}
```

### Wiring to a Server Action

After client validation passes, call the Server Action — typically by building `FormData` and invoking `formAction` from `useActionState`. The full client + server wiring is covered in **Server Actions**.

Key principle: **never trust client-only validation** — the same Zod schema should be validated again on the server.

# 22. Form Accessibility

A form should be usable by as many users as possible, including users who rely on keyboards or assistive technologies.

Important accessibility practices include:

- Use `<label>` for form fields.
- Give inputs meaningful `name` attributes.
- Use the correct input `type`.
- Provide clear error messages.
- Connect errors to the related field.
- Use buttons with meaningful text.
- Do not rely only on color to communicate errors.
- Keep keyboard navigation usable.

---

# 23. Connecting Labels and Inputs

Use:

```tsx
<label htmlFor="email">
  Email
</label>

<input
  id="email"
  name="email"
  type="email"
/>
```

The relationship is:

```text
label.htmlFor
      ↓
input.id
```

This helps assistive technologies understand which label belongs to the field.

---

# 24. Accessible Form Errors

Suppose the email is invalid.

A simple error:

```tsx
<p>Invalid email</p>
```

is better than no error, but we can make the relationship clearer.

Example:

```tsx
<label htmlFor="email">
  Email
</label>

<input
  id="email"
  name="email"
  type="email"
  aria-invalid="true"
  aria-describedby="email-error"
/>

<p id="email-error">
  Please enter a valid email address.
</p>
```

Important attributes:

```text
aria-invalid
    ↓
Indicates that the field is invalid

aria-describedby
    ↓
Connects the input to its error/help text
```

Example:

# 27. Complete Form Architecture

A practical Next.js form can follow this structure:

```text
User
  ↓
Form UI
  ↓
Client-side validation — HTML / Zod / React Hook Form
  ↓
Submission state — useFormStatus
  ↓
Server Action (Server Actions)
  ↓
Server-side validation + mutation
  ↓
Success or errors returned to UI
```

For example:

```text
React Hook Form + Zod   →  client validation
        ↓
Server Action + Zod     →  server validation (Server Actions)
        ↓
Database
```

The exact libraries are optional. The important concept is that client validation improves UX, while the server remains the final validation boundary.

# 28. Practical Signup Form

A signup form may contain:

```text
Name
Email
Password
Confirm Password
```

Validation rules:

```text
Name
 ↓
Required

Email
 ↓
Valid email

Password
 ↓
Minimum 8 characters

Confirm Password
 ↓
Must match password
```

A Zod schema could look like:

```tsx
import { z } from "zod";

const signupSchema = z
  .object({
    name: z.string().min(1, "Name is required"),
    email: z.email("Invalid email"),
    password: z
      .string()
      .min(8, "Password must be at least 8 characters"),
    confirmPassword: z.string(),
  })
  .refine(
    (data) =>
      data.password === data.confirmPassword,
    {
      path: ["confirmPassword"],
      message: "Passwords do not match",
    }
  );
```

This keeps validation rules together.

# 30. Common Mistakes

## Mistake 1: Trusting Client-Side Validation

Do not assume:

```text
Client validation = secure
```

It can be bypassed.

Always validate submitted data on the server.

---

## Mistake 2: Missing `name` Attributes

This:

```tsx
<input type="email" />
```

does not provide a field name for normal `FormData` submission.

Prefer:

```tsx
<input
  type="email"
  name="email"
/>
```

---

## Mistake 3: Showing Only a Generic Error

Avoid:

```text
Something went wrong.
```

when the user entered an invalid email.

Prefer:

```text
Email
[abc]

Please enter a valid email address.
```

Field-level errors are easier to understand and correct.

---

## Mistake 4: No Submission State

Without a pending state, users may click the button multiple times.

Provide feedback:

```text
Submit
  ↓
Submitting...
```

---

## Mistake 5: Using Client Components Unnecessarily

Not every form needs a large Client Component.

If a form can use a normal HTML submission and server-side processing, keep the client-side JavaScript as small as practical.

Use client-side libraries such as React Hook Form when their features provide real value.

---

## Mistake 6: Forgetting Accessibility

Avoid forms where:

```text
Input has no label
Error is only shown in red
Keyboard navigation is broken
```

Use semantic HTML and accessible error relationships.

---

# 31. Best Practices

### 1. Validate on the Server

Always treat server-side validation as the final validation boundary.

---

### 2. Use Client Validation for Better UX

Use client-side validation to provide fast feedback, but do not depend on it for security.

---

### 3. Keep Validation Rules Centralized

For larger forms, define a schema:

```tsx
const schema = z.object({
  email: z.email(),
  password: z.string().min(8),
});
```

This makes the rules easier to maintain.

---

### 4. Use React Hook Form When the Form Is Complex

It can be useful for:

```text
Large forms
Many fields
Dynamic fields
Complex client-side validation
Form state management
```

For a very small form, normal HTML forms may be enough.

---

### 5. Show Clear Errors

Tell the user:

```text
What went wrong?
```

and:

```text
How can they fix it?
```

---

### 6. Show Submission State

Use:

```text
Submitting...
```

or a disabled submit button while the form is being processed.

---

### 7. Keep Forms Accessible

Use:

```text
label
htmlFor
id
name
aria-invalid
aria-describedby
```

where appropriate.

# 32. Quick Comparison

| Topic | Purpose |
|---|---|
| Forms | Collect user input |
| Form Handling | Process submitted data |
| Client Validation | Give immediate feedback |
| Server Validation | Validate submitted data on the server |
| Form Errors | Tell users what needs fixing |
| Submission State | Show that submission is in progress |
| `useFormStatus` | Show pending state on submit button |
| Zod | Define and validate data schemas (client-side) |
| React Hook Form | Manage complex React forms |
| Accessibility | Make forms usable for all users |

---

# Summary

- Forms collect user input using standard HTML elements (`form`, `input`, `label`, etc.).
- Every submitted field needs a **`name` attribute**.
- Forms can submit to a Server Action via `<form action={...}>` — server-side handling is in **Server Actions**.
- Client-side validation gives users immediate feedback.
- Client-side validation can be bypassed, so server-side validation is always required (Server Actions).
- Structured field-level errors (`{ errors: { field: "..." } }`) are easier to display than one generic message.
- Submission states tell users that their request is being processed — use `useFormStatus()` for pending UI.
- Zod defines reusable validation schemas (v4 syntax: `z.email()`; v3: `z.string().email()`).
- React Hook Form manages form state, fields, errors, and submission in React.
- React Hook Form + Zod handles client-side validation; wiring to Server Actions is in Server Actions.
- HTML validation attributes such as `required` and `minLength` provide useful browser-level checks.
- Accessible forms use labels, meaningful controls, clear errors, and appropriate ARIA attributes.

## Quick Decision Guide

```text
Need a simple form?
        ↓
HTML form + Server Action (Server Actions for the action)

Need immediate client feedback?
        ↓
Add client-side validation

Need structured validation rules?
        ↓
Zod

Need complex form state?
        ↓
React Hook Form

Need both client UX and schema rules?
        ↓
React Hook Form + Zod

Need accessible forms?
        ↓
Semantic HTML
+ labels
+ clear errors
+ keyboard support
+ appropriate ARIA
```

> **Simple rule:** Use the browser and client-side validation to improve the user experience. Always validate on the server (Server Actions). Use Zod for schema rules and React Hook Form when form complexity justifies it.
