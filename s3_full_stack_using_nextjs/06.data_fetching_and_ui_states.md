# 06. Data Fetching & UI States

Modern Next.js applications often need to:

- Fetch data from APIs
- Fetch data from databases
- Show loading states
- Handle errors
- Show a not-found page
- Redirect users
- Stream UI as data becomes available

The App Router provides several built-in patterns for handling these situations.

A typical request can look like:

```text
User visits page
      ↓
Fetch data
      ↓
┌───────────────┐
│ Loading state │
└───────────────┘
      ↓
Data received
      ↓
Render UI
```

If something goes wrong:

```text
Fetch data
    ↓
Error
    ↓
Error UI
```

If the requested resource does not exist:

```text
Request resource
      ↓
Not found
      ↓
404 UI
```

---

# 1. Data Fetching

**Data fetching** means retrieving data required by a page or component.

Data can come from:

```text
External API
Database
Internal service
File / CMS
```

For example:

```text
Next.js Application
        ↓
Products API
        ↓
Product Data
        ↓
UI
```

In the App Router, Server Components are the preferred place for many initial data-fetching operations.

Example:

```tsx
async function getProducts() {
	const response = await fetch("https://fakestoreapi.com/products");

	return response.json();
}

export default async function ProductsPage() {
	const products = await getProducts();

	return (
		<div>
			{products.map((product) => (
				<p key={product.id}>{product.title}</p>
			))}
		</div>
	);
}
```

The page:

1. Runs on the server.
2. Fetches the products.
3. Receives the data.
4. Renders the UI.

> The `cache` option on `fetch` (for example `cache: "force-cache"` or `cache: "no-store"`) controls whether a fetch is treated as static or dynamic. This is covered in **Phase 8 (Caching)** and connects directly to rendering strategy from **Phase 5**.

# 2. Server-Side Data Fetching

Server-side data fetching means that data is retrieved on the server rather than by the browser.

Example:

```tsx
export default async function ProductsPage() {
	const response = await fetch("https://api.example.com/products");

	const products = await response.json();

	return (
		<div>
			{products.map((product) => (
				<p key={product.id}>{product.title}</p>
			))}
		</div>
	);
}
```

Because the component is a Server Component by default, the fetch happens on the server.

## Why Fetch on the Server?

Server-side data fetching is useful when:

- Data is needed to render the initial page.
- The API requires a secret key.
- The data comes directly from a database.
- You want to avoid exposing server credentials.
- You want to keep server-only logic away from the browser.

Example:

```text
Browser
   ↓
Next.js Server
   ↓
Private API / Database
   ↓
Next.js Server
   ↓
Rendered UI
```

The browser does not need direct access to the private data source.

## Parallel Data Fetching

When a page needs **independent** data sources, fetch them in parallel — not one after another.

Sequential fetching (slow):

```tsx
export default async function StorePage() {
	const products = await getProducts(); // waits...
	const categories = await getCategories(); // then waits again...

	return (
		<div>
			<ProductList products={products} />
			<CategoryList categories={categories} />
		</div>
	);
}
```

Parallel fetching (faster):

```tsx
export default async function StorePage() {
	const [products, categories] = await Promise.all([
		getProducts(),
		getCategories(),
	]);

	return (
		<div>
			<ProductList products={products} />
			<CategoryList categories={categories} />
		</div>
	);
}
```

Both requests run at the same time. Total wait time is roughly the **slowest** request — not the sum of both.

Use parallel fetching when the data sources do not depend on each other. If `getProduct(id)` needs a category ID from another fetch first, sequential fetching is correct.

# 3. Client-Side Data Fetching

**Client-side data fetching** means that the browser fetches data after the Client Component has loaded.

For example:

```tsx
"use client";

import { useEffect, useState } from "react";

type Product = {
	id: number;
	title: string;
};

export default function Products() {
	const [products, setProducts] = useState<Product[]>([]);

	useEffect(() => {
		fetch("https://api.example.com/products")
			.then((response) => response.json())
			.then((data) => setProducts(data));
	}, []);

	return (
		<div>
			{products.map((product) => (
				<p key={product.id}>{product.title}</p>
			))}
		</div>
	);
}
```

> Use an explicit type such as `useState<Product[]>([])`. Without it, TypeScript infers `never[]` and you get confusing errors when mapping over `products`.

The flow is:

```text
Browser
   ↓
Load Client Component
   ↓
useEffect()
   ↓
Fetch API
   ↓
Update state
   ↓
Render data
```

## When Is Client-Side Fetching Useful?

It is useful when data:

- Depends on user interaction
- Changes frequently while the user is on the page
- Is only needed after the page loads
- Is controlled by client-side state
- Is part of a highly interactive application

Examples:

```text
Live search
Interactive dashboard
Chat messages
Client-side filtering
User-specific interactions
```

> For initial page data that can be fetched on the server, prefer Server Components when appropriate. Client-side fetching should not be used automatically for every API request.

---

# 4. Server-Side vs Client-Side Data Fetching

| Server-Side Fetching             | Client-Side Fetching                 |
| -------------------------------- | ------------------------------------ |
| Runs on the server               | Runs in the browser                  |
| Good for initial page data       | Good for interactive data            |
| Can access server-only resources | Can use browser APIs                 |
| Can keep secrets on the server   | Cannot safely contain server secrets |
| Often uses Server Components     | Usually uses Client Components       |
| Useful for database access       | Useful for browser-driven updates    |

Simple rule:

```text
Initial page data
       ↓
Prefer Server-side fetching

Interactive / browser-driven data
       ↓
Consider Client-side fetching
```

# 5. Data Fetching with Query Parameters

Data can depend on search parameters.

For example:

```text
/products?category=electronics
```

On the client, read query parameters with **`useSearchParams`** and fetch when they change:

```tsx
"use client";

import { useSearchParams } from "next/navigation";
import { useEffect, useState } from "react";

export default function ProductsPage() {
	const searchParams = useSearchParams();
	const category = searchParams.get("category");
	const [products, setProducts] = useState([]);

	useEffect(() => {
		fetch(
			`https://api.example.com/products?category=${category ?? ""}`,
		)
			.then((res) => res.json())
			.then(setProducts);
	}, [category]);

	return (
		<div>
			{products.map((product) => (
				<p key={product.id}>{product.title}</p>
			))}
		</div>
	);
}
```

When the user changes the category in the URL, `category` updates and `useEffect` refetches the data.

> `useSearchParams()` is a Client Component hook. Wrap the component in `<Suspense>` if the route is statically rendered — see Phase 3 (Routing and Navigation).

# 6. Loading UI

Data fetching can take time.

Instead of showing a blank page, provide feedback to the user:

```text
Loading...
```

A good loading UI tells users that the application is working.

Loading states are especially important for:

- Slow APIs
- Database queries
- Large pages
- Navigation between routes
- Streaming content

---

# 7. `loading.tsx`

The App Router provides a special file:

```text
loading.tsx
```

It is used to create a loading UI for a route segment.

Example file structure:

```text
app/
└── products/
    ├── page.tsx
    └── loading.tsx
```

`loading.tsx`:

```tsx
export default function Loading() {
	return <p>Loading products...</p>;
}
```

When the products route is loading, Next.js can display this UI while the page content is being prepared.

## Full Example

Project:

```text
app/
├── page.tsx
└── products/
    ├── page.tsx
    └── loading.tsx
```

`page.tsx`:

```tsx
export default async function ProductsPage() {
	const response = await fetch("https://api.example.com/products");

	const products = await response.json();

	return (
		<div>
			{products.map((product) => (
				<p key={product.id}>{product.title}</p>
			))}
		</div>
	);
}
```

`loading.tsx`:

```tsx
export default function Loading() {
	return <p>Loading products...</p>;
}
```

Conceptually:

```text
/products → loading.tsx → Data fetching → page.tsx
```

---

# 8. Route-Level Loading UI

A `loading.tsx` file applies to **its route segment and all child segments** — unless a child segment defines its own `loading.tsx`.

For example:

```text
app/
├── loading.tsx          ← applies to / and all children without their own loading.tsx
├── page.tsx
│
└── dashboard/
    ├── loading.tsx      ← overrides parent for /dashboard and its children
    └── page.tsx
```

There can be:

```text
Global loading UI     → app/loading.tsx
Dashboard loading UI  → app/dashboard/loading.tsx
```

This allows different sections to have different loading experiences.

# 9. Suspense

React provides the `<Suspense>` component for showing fallback UI while part of the UI is waiting.

Example:

```tsx
import { Suspense } from "react";

function LoadingProducts() {
	return <p>Loading products...</p>;
}

export default function Page() {
	return (
		<div>
			<h1>Products</h1>

			<Suspense fallback={<LoadingProducts />}>
				<Products />
			</Suspense>
		</div>
	);
}
```

The important part is:

```tsx
<Suspense fallback={<LoadingProducts />}>
	<Products />
</Suspense>
```

While `Products` is waiting, the fallback is displayed.

---

# 10. `loading.tsx` vs Suspense

Both can show loading UI, but they are useful at different levels.

## `loading.tsx`

Use it for route-level loading UI.

```text
Route → loading.tsx → page.tsx
```

It is useful when an entire route segment is loading.

## Suspense

Use it when you want more granular loading behavior inside a page.

```text
Page
├── Header
├── Product Details
└── Reviews
       ↓
   Suspense
       ↓
   Reviews Loading
```

For example:

```tsx
export default function ProductPage() {
	return (
		<div>
			<ProductDetails />

			<Suspense fallback={<p>Loading reviews...</p>}>
				<Reviews />
			</Suspense>
		</div>
	);
}
```

This allows the product details to appear while the reviews are still loading.

---

# 11. Streaming with Suspense

**Streaming** allows the server to send the page shell to the browser immediately, then stream in content as async work inside Suspense boundaries completes.

Without streaming:

```text
Request → Wait for everything → Send complete page
```

With streaming:

```text
Request → Send page shell + ready content immediately
                ↓
          Suspense boundaries resolve independently
                ↓
          Each boundary streams in when its async work finishes
```

Example:

```tsx
import { Suspense } from "react";

export default function ProductPage() {
	return (
		<div>
			<h1>Product</h1>

			<ProductDetails />

			<Suspense fallback={<p>Loading reviews...</p>}>
				<Reviews />
			</Suspense>
		</div>
	);
}
```

Conceptually:

```text
Product Page
     │
     ├── Product Details  →  renders immediately (no Suspense boundary)
     │
     └── Reviews
             ↓
          Suspense fallback shown
             ↓
          Reviews stream in when fetch completes
```

The layout and fast content appear first. Slow sections inside `<Suspense>` boundaries stream in as their data becomes ready — not as fixed, ordered chunks.

This improves perceived performance because users do not have to wait for the slowest part of the page before seeing anything useful.

# 12. Error Handling

Data fetching can fail.

Examples:

```text
API unavailable
Database error
Network failure
Invalid response
Unexpected server error
```

Applications should provide useful error UI instead of showing a broken page.

Next.js provides:

```text
error.tsx
```

for route-level error handling.

---

# 13. `error.tsx`

An `error.tsx` file creates an error UI for a route segment.

Example file structure:

```text
app/
└── products/
    ├── page.tsx
    └── error.tsx
```

`error.tsx`:

```tsx
"use client";

export default function ErrorPage({
	error,
	reset,
}: {
	error: Error & { digest?: string };
	reset: () => void;
}) {
	return (
		<div>
			<h2>Something went wrong!</h2>

			<button onClick={() => reset()}>Try again</button>
		</div>
	);
}
```

> **Gotcha:** `error.tsx` does **not** catch errors thrown in the **root layout** (`app/layout.tsx`). For errors in the root layout, use `global-error.tsx` at `app/global-error.tsx` — it must include its own `<html>` and `<body>` tags.

---

# 14. Why `error.tsx` Is a Client Component

An error boundary needs client-side behavior such as:

```tsx
reset();
```

and often an interactive button.

Therefore, `error.tsx` must be a Client Component:

```tsx
"use client";
```

This allows the error UI to respond to user actions.

---

# 15. Error Boundaries

An **Error Boundary** catches errors that happen while rendering a part of the application and displays fallback UI instead.

Conceptually:

```text
Route
  │
  ├── Page
  │
  └── Error Boundary
          ↓
       Error?
        /   \
      No     Yes
      ↓       ↓
    Page    error.tsx
```

In Next.js, the special `error.tsx` file is used to create a route-level error boundary.

## Error Flow Example

Suppose:

```tsx
export default async function ProductsPage() {
	const response = await fetch("https://api.example.com/products");

	if (!response.ok) {
		throw new Error("Failed to fetch products");
	}

	const products = await response.json();

	return <div>Products...</div>;
}
```

If the request fails:

```text
fetch() → Error thrown → Error Boundary → error.tsx → Error UI
```

The user can see:

```text
Something went wrong!

[Try again]
```

instead of an unhandled error page.

---

# 16. `reset()` in `error.tsx`

The `reset()` function can be used to retry rendering the affected route segment.

Example:

```tsx
"use client";

export default function Error({ reset }: { reset: () => void }) {
	return (
		<div>
			<h2>Something went wrong.</h2>

			<button onClick={() => reset()}>Try again</button>
		</div>
	);
}
```

When the user clicks **Try again**, Next.js attempts to re-render the affected route segment.

# 17. `not-found.tsx`

Sometimes there is no error, but the requested resource simply does not exist.

For example:

```text
/products/123
```

If product `123` does not exist, the application should show a 404-style page.

Next.js provides:

```text
not-found.tsx
```

for this purpose.

Example file structure:

```text
app/
└── products/
    └── [id]/
        ├── page.tsx
        └── not-found.tsx
```

`not-found.tsx`:

```tsx
export default function NotFound() {
	return (
		<div>
			<h1>Product Not Found</h1>
			<p>The product you requested does not exist.</p>
		</div>
	);
}
```

---

# 18. `notFound()`

The `notFound()` function is used to trigger the nearest `not-found.tsx` UI.

Import it from:

```tsx
import { notFound } from "next/navigation";
```

Example:

```tsx
import { notFound } from "next/navigation";

export default async function ProductPage({
	params,
}: {
	params: Promise<{ id: string }>;
}) {
	const { id } = await params;

	const product = await getProduct(id);

	if (!product) {
		notFound();
	}

	return (
		<div>
			<h1>{product.name}</h1>
		</div>
	);
}
```

The flow is:

```text
Request /products/123 → Find product → Product exists?
     /       \
   Yes        No
    ↓          ↓
 Render      notFound() → not-found.tsx
```

---

# 19. `not-found.tsx` vs `error.tsx`

These two files solve different problems.

## `error.tsx`

Used when something goes wrong.

```text
API failure
Database failure
Unexpected error
```

Flow: `Error → error.tsx`

## `not-found.tsx`

Used when the requested resource does not exist.

```text
Product does not exist
User does not exist
Post does not exist
```

Flow: `notFound() → not-found.tsx`

Simple rule:

```text
Something went wrong?      → error.tsx
Resource does not exist? → not-found.tsx
```

# 20. Complete Data Fetching Flow

A typical Next.js page may use several of these features together.

Example:

```text
Request
   ↓
Server Component
   ↓
Fetch data
   │
   ├── Loading → loading.tsx
   │
   ├── Error → error.tsx
   │
   ├── Resource missing → notFound() → not-found.tsx
   │
   └── Success → Render UI
```

If the page contains slow independent sections:

```text
Page
├── Fast Content  → renders immediately
└── Slow Content  → Suspense → streams in when ready
```

For independent fetches at the top of the page, use `Promise.all` so they run in parallel.

# 21. Best Practices

## Prefer Server-Side Fetching for Initial Data

If data is required to render the initial page and can be fetched on the server, prefer a Server Component.

## Fetch Independent Data in Parallel

Use `Promise.all` when multiple fetches do not depend on each other.

## Keep Secrets on the Server

Never expose database passwords, private API keys, or secret tokens to Client Components.

## Handle API Errors

Do not blindly assume `fetch(...)` always succeeds. Check `response.ok` and throw so `error.tsx` can handle it.

## Provide Loading UI

Use `loading.tsx` for route-level loading, or `<Suspense>` for granular control inside a page.

## Use Suspense for Independent Slow Sections

If one part of the page is slow, do not make the entire page wait for it. Wrap the slow section in `<Suspense>`.

## Use `notFound()` for Missing Resources

Do not treat a missing product as a generic application error. Use `notFound()` when the resource does not exist.

## Use `redirect()` for Navigation Decisions

Use `redirect("/login")` when the user should be sent to another route. Do not wrap it in `try/catch`.

---

# Summary

- Data fetching means retrieving data required by the application.
- Server Components are a preferred place for many initial data-fetching operations.
- Fetch **independent data in parallel** with `Promise.all` — avoid slow sequential fetches.
- The `cache` option on `fetch` controls static vs dynamic behavior (Phase 8).
- Client-side fetching is useful for browser-driven and highly interactive data.
- Use `useState<Product[]>([])` (or similar) — not bare `useState([])` — to avoid TypeScript `never[]` errors.
- Databases should normally be accessed from server-side code.
- `loading.tsx` applies to its route segment **and child segments** unless a child defines its own.
- `<Suspense>` defines streaming boundaries — the page shell renders first; slow sections stream in as they complete.
- `error.tsx` provides route-level error UI but does **not** catch root layout errors — use `global-error.tsx` for that.
- `notFound()` triggers the nearest not-found UI; `redirect()` sends the user elsewhere.
- Do **not** wrap `redirect()` in `try/catch` — it throws internally and the redirect will be swallowed.
- Use Server Components for server-side data and Client Components when browser-side behavior is required.

## Quick Decision Guide

```text
Need initial page data?
        ↓
Server-side fetching

Multiple independent fetches?
        ↓
Promise.all

Need browser-driven / interactive data?
        ↓
Client-side fetching

Route is loading?
        ↓
loading.tsx

Only part of page is slow?
        ↓
Suspense + Streaming

Unexpected error?
        ↓
error.tsx (use global-error.tsx for root layout)

Resource does not exist?
        ↓
notFound() → not-found.tsx

User should go somewhere else?
        ↓
redirect() — never inside try/catch
```

> **Simple rule:** Fetch initial data on the server when appropriate, parallelize independent fetches, use Client Components for browser-driven data, provide loading and error states, use `notFound()` for missing resources, and use `redirect()` when the user needs to be sent to another route.
