# 24. Testing in Next.js

This note covers how to test a Next.js application at multiple levels — unit, integration, API, database, authentication, and end-to-end browser workflows. It builds on Jest and Supertest from the MERN stack and extends into Next.js-specific patterns for Route Handlers, Server Actions, and Playwright. The aim is confidence that important behavior works correctly, not writing the maximum number of tests.

---

## Testing in Next.js

Testing is the process of automatically verifying that application behavior matches expected behavior.

An application may include:

```text
Registration
Login
Products
Cart
Checkout
Admin Dashboard
```

Manual testing becomes repetitive:

```text
Open browser
   ↓
Login
   ↓
Open products
   ↓
Add product
   ↓
Open cart
   ↓
Checkout
```

Automated tests allow these behaviors to be verified repeatedly.

---

## Why Testing Is Important

Testing provides:

- Confidence
- Regression protection
- Safer refactoring
- Faster development
- Better documentation of expected behavior

---

## What to Test?

Test **observable behavior** — what the user or API consumer sees — not internal implementation.

| Layer | Test the behavior | Not the implementation |
| ----- | ----------------- | ---------------------- |
| Unit | `calculateTotal(items)` returns `150` | Whether it calls `reduce()` internally |
| Server Action | Invalid product name throws / returns error | Whether `revalidatePath` was called |
| Route Handler | `POST /api/products` without session → `401` | Which middleware function ran first |
| Component | Submit button shows "Saving…" while pending | Whether `useState` flipped to `true` |
| E2E | After login, dashboard shows the user's name | Which React hook triggered the render |

**Priority areas in a Next.js app:**

```text
Validation logic       → unit tests
Service + database     → integration tests
Route Handlers / APIs  → API tests (status, body, auth)
Server Actions         → unit or integration (with mocked storage)
Critical user flows    → Playwright E2E (login, checkout, admin)
```

If a refactor breaks a test but the behavior is still correct, the test was tied to implementation — rewrite it to assert the outcome instead.

---

## Testing Pyramid

A useful mental model is:

```text
                 E2E Tests
               /           \
              /             \
        Integration Tests
          /             \
         /               \
       Unit Tests
```

Generally:

```text
Many unit tests
Some integration/API tests
Fewer E2E tests
```

Unit tests are usually faster and cheaper.

E2E tests are slower and can be more fragile.

Therefore, use each testing level for the right purpose.

## Testing Levels

The sections below are numbered by testing level:

```text
1. Unit Testing
2. Integration Testing
3. API Testing
4. Database Testing
5. Authentication Testing
6. End-to-End Testing
```

These levels can overlap — an API test may hit a Route Handler, service layer, and test database in one run.

## 1. Unit Testing

Unit testing verifies a small, isolated piece of code.

Good candidates include:

```text
Functions
Validators
Formatters
Calculations
Business rules
Data transformations
Utilities
```

Example:

```ts
export function calculateTotal(price: number, quantity: number) {
	return price * quantity;
}
```

Test:

```ts
describe("calculateTotal", () => {
	it("calculates the total price", () => {
		expect(calculateTotal(100, 3)).toBe(300);
	});
});
```

The test focuses only on the function.

---

### 1.1 Unit Test Characteristics

A good unit test is generally:

```text
Independent
Fast
Deterministic
Focused
Easy to understand
```

Ideally it does not require:

```text
Real database
Real network
Real browser
Real payment provider
```

unless those dependencies are specifically what the test is intended to verify.

---

### 1.2 Arrange, Act, Assert

A common unit-test pattern is:

```text
Arrange
   ↓
Act
   ↓
Assert
```

Example:

```ts
it("calculates order total", () => {
	// Arrange
	const price = 100;
	const quantity = 3;

	// Act
	const total = calculateTotal(price, quantity);

	// Assert
	expect(total).toBe(300);
});
```

This structure makes tests easier to read.

---

### 1.3 Test Suites and Test Cases

A test suite groups related tests.

```ts
describe("calculateTotal", () => {
	it("calculates total for one item", () => {
		// ...
	});

	it("calculates total for multiple items", () => {
		// ...
	});

	it("handles zero quantity", () => {
		// ...
	});
});
```

Conceptually:

```text
describe
   ↓
Test Suite
   ├── Test Case
   ├── Test Case
   └── Test Case
```

---

### 1.4 Positive, Negative, and Edge Cases

Do not test only successful scenarios.

### 1.4.1 Positive case

```text
Valid input
   ↓
Expected result
```

### 1.4.2 Negative case

```text
Invalid input
   ↓
Expected error
```

### 1.4.3 Edge case

```text
Boundary/unusual input
   ↓
Expected behavior
```

Examples:

```text
0
1
Negative value
Very large value
Empty string
Null
Undefined
Empty array
Duplicate value
Invalid format
```

---

### 1.5 Unit Testing Utilities

Example:

```ts
export function formatPrice(amount: number) {
	return `$${amount.toFixed(2)}`;
}
```

Tests:

```ts
describe("formatPrice", () => {
	it("formats integer price", () => {
		expect(formatPrice(100)).toBe("$100.00");
	});

	it("formats decimal price", () => {
		expect(formatPrice(99.5)).toBe("$99.50");
	});
});
```

---

### 1.6 Unit Testing Validation

Example:

```ts
export function isValidEmail(email: string) {
	return /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(email);
}
```

Tests:

```ts
describe("isValidEmail", () => {
	it("accepts valid email", () => {
		expect(isValidEmail("user@example.com")).toBe(true);
	});

	it("rejects invalid email", () => {
		expect(isValidEmail("invalid-email")).toBe(false);
	});
});
```

---

### 1.7 Unit Testing Business Logic

Example:

```ts
export function calculateDiscount(total: number) {
	if (total >= 1000) {
		return total * 0.1;
	}

	return 0;
}
```

Test both branches:

```ts
describe("calculateDiscount", () => {
	it("does not apply discount below 1000", () => {
		expect(calculateDiscount(500)).toBe(0);
	});

	it("applies 10 percent discount at 1000", () => {
		expect(calculateDiscount(1000)).toBe(100);
	});
});
```

## 2. Integration Testing

Integration testing verifies that multiple parts work together.

Examples:

```text
Service
   ↓
Repository
   ↓
Database
```

or:

```text
Route Handler
   ↓
Service
   ↓
Repository
   ↓
Database
```

Unlike a unit test, integration testing intentionally includes multiple components.

---

### 2.1 Unit vs Integration Testing

### 2.1.1 Unit

```text
Function
   ↓
Result
```

Question:

```text
Does this individual piece work?
```

### 2.1.2 Integration

```text
Service
   ↓
Repository
   ↓
Database
   ↓
Result
```

Question:

```text
Do these pieces work correctly together?
```

---

### 2.2 Integration Testing Example

Suppose:

```ts
async function createUser(data: CreateUserInput) {
	const hashedPassword = await hashPassword(data.password);

	return userRepository.create({
		...data,
		password: hashedPassword,
	});
}
```

An integration test may verify:

```text
createUser()
    ↓
Password hashing
    ↓
Repository
    ↓
Database
    ↓
User exists
```

This is more realistic than mocking every internal dependency.

---

### 2.3 Mocks

A mock replaces a dependency with a controlled fake implementation.

Example:

```text
Application
   ↓
Payment Service
```

During a test:

```text
Application
   ↓
Mock Payment Service
```

Mocks are useful when:

- A real service is expensive
- A service is unavailable
- A side effect is dangerous
- A deterministic response is required
- The dependency is outside your system

---

### 2.4 When Not to Mock

Over-mocking can make tests unrealistic.

For example:

```text
Mock database
Mock repository
Mock service
Mock authentication
```

The test may pass even though the real components do not work together.

A useful rule:

> Mock external systems when necessary, but allow important internal components to integrate when the integration itself is what you want to verify.

---

## 3. API Testing

API testing verifies HTTP endpoints.

For example:

```text
POST /api/products
```

Test:

```text
Request
   ↓
Route Handler
   ↓
Response
```

Verify:

- Status code
- Response body
- Headers
- Validation
- Authentication
- Authorization
- Error handling
- Database side effects

---

### 3.1 API Test Cases

For:

```text
POST /api/products
```

test:

### 3.1.1 Successful request

```text
Valid body
   ↓
201 Created
```

### 3.1.2 Invalid request

```text
Invalid body
   ↓
400 Bad Request
```

### 3.1.3 Unauthenticated

```text
No session
   ↓
401 Unauthorized
```

### 3.1.4 Unauthorized

```text
Authenticated but insufficient permission
   ↓
403 Forbidden
```

### 3.1.5 Duplicate resource

```text
Existing unique value
   ↓
409 Conflict
```

---

### 3.2 HTTP Status Code Testing

Example:

```ts
expect(response.status).toBe(201);
```

Common status codes:

```text
200 OK
201 Created
204 No Content
400 Bad Request
401 Unauthorized
403 Forbidden
404 Not Found
409 Conflict
422 Unprocessable Content
429 Too Many Requests
500 Internal Server Error
```

Use the status code that matches the API contract.

---

### 3.3 API Response Testing

Do not only check the status code.

Example:

```ts
const body = await response.json();

expect(body).toMatchObject({
	id: expect.any(String),
	email: "user@example.com",
});
```

This catches accidental response-contract changes.

---

### 3.4 API Validation Testing

Suppose:

```text
POST /api/products
```

expects:

```json
{
	"name": "Laptop",
	"price": 1000
}
```

Test:

```text
Missing name
Missing price
Negative price
Wrong data type
Empty name
Malformed JSON
Unexpected input
```

The API should reject invalid input.

---

### 3.5 Testing Route Handlers

Example:

```ts
export async function POST(request: Request) {
	const body = await request.json();

	// validation
	// service call

	return Response.json(
		{
			message: "Created",
		},
		{
			status: 201,
		},
	);
}
```

The test should verify observable HTTP behavior:

```text
HTTP Request
   ↓
Route Handler
   ↓
HTTP Response
```

---

### 3.6 API Integration Testing

A realistic API integration test can involve:

```text
HTTP Request
   ↓
Route Handler
   ↓
Service
   ↓
Repository
   ↓
Test Database
   ↓
HTTP Response
```

This verifies that the API and backend layers work together.

---

## 4. Database Testing

Database testing verifies that application code correctly interacts with the database.

Test:

```text
Create
Read
Update
Delete
Relationships
Constraints
Transactions
```

Example:

```text
User
   ↓
Create
   ↓
Database
   ↓
Read
   ↓
Verify
```

---

### 4.1 Why Test the Database?

A unit test may say:

```text
repository.create()
returns expected object
```

But the real database may fail because of:

```text
Wrong schema
Constraint violation
Incorrect query
Migration problem
Relation problem
Transaction problem
```

Database integration tests catch these issues.

---

### 4.2 Test Database vs Production Database

Never run destructive automated tests against production.

Use:

```text
Development DB
Test DB
Production DB
```

Example:

```env
# Test environment
DATABASE_URL=postgresql://...test...
```

The test database should be isolated.

---

### 4.3 Database Test Lifecycle

A common lifecycle is:

```text
Prepare test database
        ↓
Create required test data
        ↓
Run test
        ↓
Clean up
        ↓
Next test
```

Another strategy is:

```text
Begin transaction
      ↓
Run test
      ↓
Rollback
```

Choose the approach appropriate for the database and application.

---

### 4.4 Testing CRUD

Suppose the application has:

```text
User
```

Test:

```text
CREATE
 ↓
User created

READ
 ↓
User retrieved

UPDATE
 ↓
User changed

DELETE
 ↓
User removed
```

This verifies database behavior.

---

### 4.5 Testing Database Constraints

Suppose:

```text
email UNIQUE
```

Test:

```text
Create user
    ↓
Create second user
with same email
    ↓
Database rejects operation
```

The test verifies that the database constraint actually protects the data.

---

### 4.6 Testing Relationships

Suppose:

```text
User
  │
  └── Orders
```

Test:

```text
Create user
   ↓
Create order for user
   ↓
Fetch user with orders
   ↓
Verify relationship
```

This is especially useful with Prisma relations.

---

### 4.7 Testing Transactions

Suppose creating an order requires:

```text
Create Order
+
Reduce Inventory
+
Create Payment Record
```

These operations should succeed together or fail together.

Test:

```text
Start Transaction
      ↓
Create Order
      ↓
Reduce Inventory
      ↓
Failure
      ↓
Rollback
```

Verify that partial data was not left behind.

---

### 4.8 Database Test Isolation

Tests should not depend on previous tests.

Bad:

```text
Test A creates user
       ↓
Test B assumes user exists
```

Better:

```text
Test A
 ↓
Own setup
 ↓
Own cleanup

Test B
 ↓
Own setup
 ↓
Own cleanup
```

Independent tests are easier to debug and can run safely in parallel.

## 5. Authentication Testing

Authentication testing verifies:

```text
Registration
Login
Logout
Sessions
Cookies
Password handling
Protected resources
```

Authentication should be tested at multiple levels.

---

### 5.1 Registration Testing

Test:

```text
Valid registration
    ↓
User created
```

Also test:

```text
Invalid email
Weak password
Missing fields
Existing email
Malformed request
```

Example:

```text
POST /api/auth/register
```

---

### 5.2 Password Testing

Never test by expecting the raw password to be stored.

Correct model:

```text
Password
   ↓
Hash
   ↓
Database
```

Test:

```text
Correct password → verification succeeds
Wrong password   → verification fails
Raw password     → not stored
```

Example:

```ts
expect(storedPassword).not.toBe("password123");
```

---

### 5.3 Login Testing

Test:

```text
Correct email
+
Correct password
      ↓
Login successful
```

Also:

```text
Wrong password
Unknown email
Missing credentials
Malformed request
Disabled account
```

---

### 5.4 Session Testing

After login:

```text
Login
 ↓
Session created
 ↓
Cookie/session stored
 ↓
Protected request
 ↓
Authenticated
```

Test:

```text
Valid session   → allowed
Invalid session → rejected
Expired session → rejected
Missing session → rejected
```

---

### 5.5 Cookie Testing

If authentication uses cookies, verify important properties when applicable:

```text
HttpOnly
Secure
SameSite
Path
Expiration / Max-Age
```

Sensitive session cookies should generally use `HttpOnly` where appropriate so client-side JavaScript cannot directly read them.

Security expectations should still be evaluated against the deployment environment.

---

### 5.6 Protected Route Testing

Suppose:

```text
GET /api/profile
```

requires authentication.

Test:

```text
No session
   ↓
401
```

and:

```text
Valid session
   ↓
200
```

Also test:

```text
Invalid/expired session
   ↓
401
```

---

### 5.7 Authentication vs Authorization Testing

These are different.

### 5.7.1 Authentication

```text
Is the user logged in?
```

### 5.7.2 Authorization

```text
Is this user allowed to perform this action?
```

Example:

```text
User A → logged in → Yes
User A → delete another user → No
```

Typical API semantics:

```text
401 → Not authenticated

403 → Authenticated but not authorized
```

---

### 5.8 Authorization Testing

Suppose:

```text
ADMIN
USER
```

Test:

```text
ADMIN → /admin → allowed
USER  → /admin → forbidden
```

Also test object-level authorization:

```text
User A
 ↓
Attempt to access User B's private resource
 ↓
Rejected
```

This helps detect broken access-control vulnerabilities.

## 6. End-to-End Testing

End-to-End testing verifies a complete user workflow.

Example:

```text
Open browser
   ↓
Open login page
   ↓
Enter email
   ↓
Enter password
   ↓
Click Login
   ↓
Dashboard opens
   ↓
Create product
   ↓
Product appears
```

Unlike a unit test, E2E testing verifies the application from the user's perspective.

---

### 6.1 Why E2E Testing Is Important

E2E tests can catch failures across multiple layers:

```text
Frontend
   ↓
Routing
   ↓
Authentication
   ↓
API
   ↓
Database
   ↓
UI update
```

Individual unit tests may all pass while the complete workflow is broken.

---

### 6.2 Playwright

Playwright is a browser automation and end-to-end testing framework.

It supports major browser engines such as:

```text
Chromium
Firefox
WebKit
```

It can automate:

```text
Navigation
Clicking
Typing
Form submission
File uploads
Assertions
Screenshots
Multiple pages
Browser contexts
```

This makes it well suited for testing Next.js applications.

---

### 6.3 Playwright Installation

A typical Playwright setup starts with:

```bash
npm init playwright@latest
```

or the equivalent command for the package manager being used.

A project commonly contains:

```text
tests/
├── auth.spec.ts
├── products.spec.ts
└── checkout.spec.ts

playwright.config.ts
```

The generated setup may differ depending on the Playwright version.

---

### 6.4 First Playwright Test

Example:

```ts
import { test, expect } from "@playwright/test";

test("user can open products", async ({ page }) => {
	await page.goto("/products");

	await expect(
		page.getByRole("heading", {
			name: "Products",
		}),
	).toBeVisible();
});
```

The test:

```text
Open page
   ↓
Find heading
   ↓
Verify heading is visible
```

---

### 6.5 Playwright `page`

The `page` object represents a browser page.

Example:

```ts
await page.goto("/login");

await page.getByLabel("Email").fill("user@example.com");

await page.getByLabel("Password").fill("password123");
```

It can perform browser operations such as:

```text
goto()
click()
fill()
check()
selectOption()
setInputFiles()
```

---

### 6.6 Playwright Locators

Locators identify elements.

Prefer user-facing locators:

```ts
page.getByRole("button", {
	name: "Login",
});

page.getByLabel("Email");

page.getByText("Products");

page.getByPlaceholder("Enter your email");
```

Prefer meaningful accessibility-based locators over fragile CSS selectors.

---

### 6.7 Why Good Locators Matter

Fragile:

```ts
page.locator(".btn-primary:nth-child(2)");
```

Better:

```ts
page.getByRole("button", {
	name: "Login",
});
```

Good locators describe how a user understands the interface and are usually more resilient to implementation changes.

---

### 6.8 Playwright Assertions

Example:

```ts
await expect(page.getByText("Product created")).toBeVisible();
```

Other examples:

```ts
await expect(page).toHaveURL(/dashboard/);

await expect(
	page.getByRole("button", {
		name: "Submit",
	}),
).toBeEnabled();

await expect(page.getByLabel("Email")).toHaveValue("user@example.com");
```

---

### 6.9 Testing Login with Playwright

Example:

```ts
test("user can login", async ({ page }) => {
	await page.goto("/login");

	await page.getByLabel("Email").fill("user@example.com");

	await page.getByLabel("Password").fill("password123");

	await page
		.getByRole("button", {
			name: "Login",
		})
		.click();

	await expect(page).toHaveURL(/dashboard/);
});
```

This tests the complete login workflow.

---

### 6.10 Testing Validation with Playwright

Example:

```ts
test("login shows validation error", async ({ page }) => {
	await page.goto("/login");

	await page
		.getByRole("button", {
			name: "Login",
		})
		.click();

	await expect(page.getByText("Email is required")).toBeVisible();
});
```

Test visible behavior rather than internal component state.

### 6.14 Testing Protected Pages

Unauthenticated test:

```ts

```

This verifies:

```text

 ↓

 ↓

Redirect
```

### 6.15 Testing Authenticated Pages

You can authenticate before running tests and reuse browser authentication state.

Conceptually:

```text
Login
 ↓
Save authentication state
 ↓
Reuse session
 ↓
Run protected tests
```

Playwright supports reusable authentication state containing browser state such as cookies and storage.

Never commit real production authentication state or credentials to source control.

### 6.16 Test Fixtures

Fixtures provide reusable test setup.

Examples:

```text

Admin user
Database setup
Test data
Browser configuration
```

This avoids repeating the same setup code in many tests.

### 6.17 E2E Test Data

E2E tests need predictable data.

Possible strategies:

```text

```

```text

   ↓

```

## Testing External APIs

Suppose:

```text
Next.js
   ↓
Payment API
```

During most automated tests, it may be better to mock or intercept the external API:

```text
Next.js
   ↓
Mock Payment API
   ↓
Predictable response
```

Simulate:

```text

400 error
500 error
Timeout
Empty response
Malformed response
```

Keep a smaller number of integration/contract tests against a real sandbox when needed.

Do not normally send real emails to real users during automated tests.

Instead test:

```text
Application
   ↓
Email Service
   ↓
Expected email request
```

An E2E environment can use a dedicated test email provider or mailbox.

Example workflow:

```text
Register
 ↓
Verification email generated
 ↓
Test mailbox
 ↓
Open verification link
```

Use:

```text
Provider test mode
Sandbox
Mock provider
Test accounts

```

Test:

```text
Successful payment
Declined payment
Cancelled payment
Timeout/failure
```

## Test Environment

Automated tests should be isolated from production.

Example:

```text
Development
    ↓
Development resources

Test
    ↓
Test resources

Production
    ↓
Production resources
```

A test environment should use:

```text

Test API credentials
Test storage

```

Never point destructive automated tests at production.

---

## Unit vs Integration vs E2E

| Type           | Scope                   |     Speed | Typical dependencies |
| -------------- | ----------------------- | --------: | -------------------- |
| Unit           | Small function/module   | Very fast | Usually none         |
| Integration    | Multiple internal parts |    Medium | Test DB/services     |
| API            | HTTP endpoint           |    Medium | App + test resources |
| Database       | Database behavior       |    Medium | Test DB              |
| Authentication | Auth/session behavior   |    Medium | Auth + DB            |
| E2E            | Complete user flow      |      Slow | Browser + app        |

---

## What to Unit Test

Good candidates:

```text
Pure functions
Validators
Formatters
Calculations
Business rules
Data transformations
Utility functions
```

Examples:


## Testing Accessibility

Good Playwright locators naturally encourage accessible interfaces.

## Avoid Hard-Coded Sleeps

Avoid:

```ts
await page.waitForTimeout(5000);
```

This makes tests:

```text
Slow
Flaky
Environment-dependent
```

Prefer waiting for a meaningful condition:

```ts
await expect(page.getByText("Completed")).toBeVisible();
```

Wait for the behavior you actually expect.

## Flaky Tests

A flaky test sometimes passes and sometimes fails without code changes.

Common causes:

```text
Timing issues
Race conditions
Shared test data
External services
Random data
Network dependency
Hard-coded waits
Unstable selectors
```

Do not simply add retries and ignore the problem.

Find the root cause.

---

## Test Retries

Retries can help diagnose or reduce environmental flakiness in CI.

But:

```text
Retry ≠ Fix
```

If a test fails because of a real application bug, retries should not hide it.

Use retries carefully.

---

## Deterministic Tests

A deterministic test should produce the same result under the same conditions.

Avoid uncontrolled:

```text
Current time
Random values
Real network
Production database
External provider availability
```

when they are not part of what is being tested.

Use controlled:

```text
Fixed test data
Test database
Mock external APIs
Controlled time
```

when appropriate.

---

## Independent Tests

Avoid:

```text
Test A creates data
Test B depends on Test A
Test C depends on Test B
```

Prefer:

```text
Test A
 ↓
Own setup
 ↓
Own assertions

Test B
 ↓
Own setup
 ↓
Own assertions
```

Independent tests are easier to debug and parallelize.

## Contract Testing

When your application depends on an API, the expected response shape is effectively a contract.

Example:

```json
{
	"id": "123",
	"name": "Laptop",
	"price": 999
}
```

If the provider changes it to:

```json
{
	"product_id": "123",
	"title": "Laptop",
	"amount": 999
}
```

your application may break.

Contract tests can detect such changes.

## Final Mental Model

Think of testing as multiple layers:

```text
                    User
                     │
                     ▼
                E2E Testing
                     │
                     ▼
                API Testing
                     │
                     ▼
             Integration Testing
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
       Service              Repository
          │                     │
          └──────────┬──────────┘
                     ▼
                Test Database
```

Unit tests sit underneath the architecture:

```text
Unit Tests
    ↓
Small isolated pieces of logic
```

The key question at each level is:

```text
Unit
→ Does this piece of logic work?

Integration
→ Do these pieces work together?

API
→ Does this HTTP endpoint behave correctly?

Database
→ Does persistence work correctly?

Authentication
→ Can the right users authenticate and maintain sessions?

Authorization
→ Can only permitted users perform protected actions?

E2E
→ Can a real user successfully complete the workflow?
```

## Final Summary

A strong Next.js testing strategy looks like:

```text
Unit
 ↓
Fast verification of individual logic

Integration
 ↓
Verify internal components work together

API
 ↓
Verify HTTP contracts and server behavior

Database
 ↓
Verify real persistence behavior

Authentication
 ↓
Verify login, sessions, cookies, and protected resources

E2E / Playwright
 ↓
Verify complete user journeys
```

Key points:

> **Do not solve every testing problem with E2E tests.**

> **Do not solve every testing problem with unit tests.**

> **Use the lowest appropriate testing level for each behavior.**

> **Test behavior rather than implementation details.**

> **Authentication and authorization are security boundaries and deserve explicit tests.**

> **E2E tests should focus on important user journeys rather than every small UI detail.**

> **A good test suite makes it safe to change the application without silently breaking important behavior.**
