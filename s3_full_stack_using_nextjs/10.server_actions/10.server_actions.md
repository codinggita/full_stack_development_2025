# 10. Server Actions

Server Actions handle what happens when a form's `action` fires. Build the form first — see **Forms & Validation** for form structure and client-side validation.

Server Actions are functions that run on the server and can be called from Client Components, Server Components, or forms depending on how they are defined and used.

They are useful when the frontend needs to perform a server-side operation such as:

- Creating a record
- Updating a record
- Deleting a record
- Submitting a form
- Updating user settings
- Performing other server-side mutations

A simple flow is:

```text
User
 ↓
Form / Client UI
 ↓
Server Action
 ↓
Validate data
 ↓
Perform mutation
 ↓
Revalidate / Redirect
 ↓
Return result
```

---

# 1. What Are Server Actions?

A **Server Action** is an asynchronous server-side function that can be invoked from the application.

For example:

```tsx
"use server";

export async function createUser(formData: FormData) {
	const email = formData.get("email");

	// Server-side logic
}
```

The important idea is:

```text
Server Action
      ↓
Runs on the server
```

This means the function can perform server-side operations that should not be exposed as normal browser-only logic.

For example:

```text
Server Action
     ↓
Validate input
     ↓
Access database
     ↓
Update database
```

---

# 2. Why Use Server Actions?

Before Server Actions, a common approach was:

```text
Client Component
      ↓
fetch()
      ↓
API Route
      ↓
Database
```

Server Actions can simplify some server-side mutations:

```text
Client / Form
      ↓
Server Action
      ↓
Database
```

This can reduce the amount of API endpoint code required for operations that are only needed by the Next.js application itself.

Server Actions are especially useful for:

- Form submissions
- Create operations
- Update operations
- Delete operations
- Server-side mutations

---

# 3. `"use server"`

The directive:

```tsx
"use server";
```

tells Next.js that the function should execute on the server.

Example:

```tsx
"use server";

export async function createProduct(formData: FormData) {
	// Server-side code
}
```

The directive can be used at the top of a file:

```tsx
"use server";

export async function createProduct() {
	// ...
}

export async function deleteProduct() {
	// ...
}
```

This marks the exported functions in the file as Server Actions.

You can also place the directive **inside a single function** instead of at the top of the file:

```tsx
export async function createProduct(formData: FormData) {
	"use server";

	const name = formData.get("name");
	// Server-side code
}
```

This marks only that function as a Server Action — useful when you want one server function in a file without marking every export.

---

# 4. Server Actions with Forms

One of the most common uses of Server Actions is handling forms.

Example:

```tsx
"use server";

export async function createUser(formData: FormData) {
	const email = formData.get("email");

	console.log(email);
}
```

The form can use the action:

```tsx
import { createUser } from "./actions";

export default function SignupForm() {
	return (
		<form action={createUser}>
			<input type='email' name='email' />

			<button type='submit'>Create Account</button>
		</form>
	);
}
```

The flow is:

```text
User fills form
      ↓
Submit
      ↓
Server Action
      ↓
FormData
      ↓
Server-side processing
```

# 5. Reading Form Data

A form submission provides a `FormData` object.

Example:

```tsx
"use server";

export async function login(formData: FormData) {
	const email = formData.get("email");
	const password = formData.get("password");

	console.log(email);
	console.log(password);
}
```

The form fields should have `name` attributes:

```tsx
<input
  type="email"
  name="email"
/>

<input
  type="password"
  name="password"
/>
```

Then:

```tsx
formData.get("email");
```

retrieves the submitted email.

# 6. Server-Side Mutations

A **mutation** means changing data.

For example:

```text
Create
Update
Delete
```

These are all mutations.

Suppose a product is stored in a database:

```text
Product
id: 101
name: Laptop
price: 50000
```

An update operation:

```text
price: 50000
        ↓
price: 45000
```

is a mutation.

A Server Action can perform this operation:

```tsx
"use server";

export async function updateProduct(id: string, price: number) {
	await db.product.update({
		where: {
			id,
		},
		data: {
			price,
		},
	});
}
```

The important flow is:

```text
Client
 ↓
Server Action
 ↓
Database mutation
```

---

# 7. Create, Update and Delete

Server Actions can be used for common CRUD mutations.

### Create

```tsx
"use server";

export async function createProduct(formData: FormData) {
	const name = formData.get("name");

	await db.product.create({
		data: {
			name: String(name),
		},
	});
}
```

### Update

```tsx
"use server";

export async function updateProduct(id: string, formData: FormData) {
	const name = formData.get("name");

	await db.product.update({
		where: { id },
		data: {
			name: String(name),
		},
	});
}
```

A `<form>` action only passes `FormData` — it cannot supply extra arguments like `id`. Use **`.bind()`** to pre-fill them:

```tsx
const updateProductWithId = updateProduct.bind(null, id);
```

```tsx
<form action={updateProductWithId}>
	<input name='name' />
	<button type='submit'>Update</button>
</form>
```

`.bind(null, id)` creates a new function where `id` is already the first argument; the form submission still supplies `formData` as the second.

### Delete

```tsx
"use server";

export async function deleteProduct(id: string) {
	await db.product.delete({
		where: { id },
	});
}
```

These operations are server-side mutations.

# 8. Validation in Server Actions

Never trust data received by a Server Action.

Even if the form has client-side validation:

```text
Client validation
      ↓
Can be bypassed
```

Therefore, validate data inside the Server Action before performing the mutation.

Example:

```tsx
"use server";

import { z } from "zod";

const schema = z.object({
	email: z.email(),
	password: z.string().min(8),
});

export async function createUser(formData: FormData) {
	const result = schema.safeParse({
		email: formData.get("email"),
		password: formData.get("password"),
	});

	if (!result.success) {
		return {
			error: "Invalid form data",
		};
	}

	// Perform mutation
}
```

The flow is:

```text
FormData
   ↓
Server Action
   ↓
Validate
   ↓
Valid?
 /    \
No     Yes
↓       ↓
Error   Mutation
```

---

# 9. Why Validate Inside Server Actions?

A Server Action is still receiving input from the client.

The client can potentially send unexpected data.

For example, the UI may require:

```text
price >= 0
```

but someone could send:

```text
price = -500
```

directly to the server.

Therefore:

```text
Client validation
       ↓
Better UX

Server validation
       ↓
Protect application data
```

Both can be useful, but server-side validation is essential.

---

# 10. Using Zod with Server Actions

Zod is useful for defining validation rules.

Example:

```tsx
import { z } from "zod";

const productSchema = z.object({
	name: z.string().min(1),
	price: z.number().positive(),
});
```

The Server Action can validate data before updating the database:

```tsx
"use server";

export async function createProduct(formData: FormData) {
	const result = productSchema.safeParse({
		name: formData.get("name"),
		price: Number(formData.get("price")),
	});

	if (!result.success) {
		return {
			errors: result.error.flatten().fieldErrors,
		};
	}

	await db.product.create({
		data: result.data,
	});
}
```

This keeps the validation rules explicit.

# 11. Returning Errors from Server Actions

A Server Action can return a result describing whether the operation succeeded.

For example:

```tsx
"use server";

export async function createUser(formData: FormData) {
	const email = formData.get("email");

	if (!email) {
		return {
			error: "Email is required",
		};
	}

	// Create user...

	return {
		success: true,
	};
}
```

The client can use the result to show an appropriate message.

For field-level errors, a structured result is often better:

```tsx
return {
	errors: {
		email: "Email is required",
		password: "Password is too short",
	},
};
```

# 12. `useActionState`

When a Server Action returns `{ error }` or `{ errors }`, the Client Component needs a way to receive that return value. **`useActionState`** connects the action's result to React state.

The action signature changes slightly — it receives `(prevState, formData)` and returns the next state object:

```tsx
"use server";

type FormState = {
	error?: string;
	errors?: Record<string, string | string[]>;
	success?: boolean;
};

export async function createUser(
	prevState: FormState,
	formData: FormData,
): Promise<FormState> {
	const email = formData.get("email");

	if (!email) {
		return {
			errors: {
				email: "Email is required",
			},
		};
	}

	// Create user...

	return { success: true };
}
```

> When using Zod's `flatten().fieldErrors`, each field maps to `string[]` — display with `state.errors?.field?.[0]`. **Combining with React Hook Form** shows the full pattern.

In a Client Component, pass the action to `useActionState` and wire **`formAction`** (not the raw action) to the form:

```tsx
"use client";

import { useActionState } from "react";
import { createUser } from "./actions";

export default function SignupForm() {
	const [state, formAction, pending] = useActionState(createUser, {});

	return (
		<form action={formAction}>
			<label htmlFor='email'>Email</label>
			<input id='email' name='email' type='email' />
			{state.errors?.email && (
				<p role='alert'>
					{Array.isArray(state.errors.email)
						? state.errors.email[0]
						: state.errors.email}
				</p>
			)}
			{state.error && <p role='alert'>{state.error}</p>}
			{state.success && <p>Account created!</p>}

			<button type='submit' disabled={pending}>
				{pending ? "Creating..." : "Sign up"}
			</button>
		</form>
	);
}
```

Key points:

- Pass **`formAction`** to `<form action={...}>`, not the raw Server Action.
- **`state`** holds whatever the action returned on the last submission.
- **`pending`** is `true` while the action is running — use it for loading UI.
- For React Hook Form or other non-native submit flows, call `formAction(formData)` inside `startTransition` instead of using `<form action>` directly.

# 13. Combining with React Hook Form

React Hook Form's **`handleSubmit`** takes over form submission and calls your `onValid` function with parsed data — it does not use the native `<form action={formAction}>` wiring that `useActionState` expects by default. To use both together, build `FormData` manually inside `onValid` and pass it to `formAction`, wrapped in **`startTransition`**.

Adapt the **`createProduct`** action from **Using Zod with Server Actions** to the `useActionState` signature — here with a server-only duplicate-name check:

```tsx
"use server";

import { z } from "zod";

const productSchema = z.object({
	name: z.string().min(1, "Name is required"),
	price: z.coerce.number().min(0, "Price must be positive"),
});

type FormState = {
	errors?: Record<string, string[]>;
	success?: boolean;
};

export async function createProduct(
	prevState: FormState,
	formData: FormData,
): Promise<FormState> {
	const result = productSchema.safeParse({
		name: formData.get("name"),
		price: formData.get("price"),
	});

	if (!result.success) {
		return { errors: result.error.flatten().fieldErrors };
	}

	const exists = await db.product.findFirst({
		where: { name: result.data.name },
	});
	if (exists) {
		return {
			errors: { name: ["A product with this name already exists"] },
		};
	}

	await db.product.create({ data: result.data });
	return { success: true };
}
```

Client Component — same `name` / `price` schema as in **Forms & Validation** (**React Hook Form + Server Actions**):

```tsx
"use client";

import { useActionState, startTransition } from "react";
import { useForm } from "react-hook-form";
import { zodResolver } from "@hookform/resolvers/zod";
import { z } from "zod";
import { createProduct } from "./actions";

const schema = z.object({
	name: z.string().min(1, "Name is required"),
	price: z.coerce.number().min(0, "Price must be positive"),
});

type FormValues = z.infer<typeof schema>;

export default function ProductForm() {
	const [state, formAction, pending] = useActionState(createProduct, {});

	const {
		register,
		handleSubmit,
		formState: { errors },
	} = useForm<FormValues>({ resolver: zodResolver(schema) });

	function onValid(data: FormValues) {
		const fd = new FormData();
		Object.entries(data).forEach(([key, value]) => {
			fd.append(key, String(value));
		});
		startTransition(() => formAction(fd));
	}

	return (
		<form onSubmit={handleSubmit(onValid)} noValidate>
			<label htmlFor='name'>Name</label>
			<input id='name' {...register("name")} />
			{errors.name && <p role='alert'>{errors.name.message}</p>}
			{state.errors?.name?.[0] && (
				<p role='alert'>{state.errors.name[0]}</p>
			)}

			<label htmlFor='price'>Price</label>
			<input id='price' type='number' {...register("price")} />
			{errors.price && <p role='alert'>{errors.price.message}</p>}

			{state.success && <p>Product created!</p>}

			<button type='submit' disabled={pending}>
				{pending ? "Saving..." : "Save"}
			</button>
		</form>
	);
}
```

**Why both error sources?** RHF's **`errors`** catch client-side validation before submission. **`state.errors`** catch anything only the server can know — uniqueness checks, business rules, tampered data — so a complete form shows both, not just one.

# 14. Calling Server Actions Outside a Form

Not every Server Action is triggered by a `<form>` submit. Buttons like "Like", "Add to cart", or quantity steppers can call an action directly from an event handler.

Wrap the call in **`startTransition`** so React treats it as a non-urgent update and keeps the UI responsive:

```tsx
"use client";

import { startTransition } from "react";
import { likePost } from "./actions";

export function LikeButton({ postId }: { postId: string }) {
	return (
		<button
			type='button'
			onClick={() => startTransition(() => likePost(postId))}
		>
			Like
		</button>
	);
}
```

```tsx
"use server";

export async function likePost(postId: string) {
	// await db.like.create({ postId, userId });
}
```

The same auth and validation rules apply — a Server Action is still a server endpoint whether it is called from a form or a button click.

# 15. Error Handling in Server Actions

Errors can happen for many reasons:

```text
Invalid input
Database failure
Authentication failure
Authorization failure
External API failure
Unexpected server error
```

A Server Action should handle expected errors carefully.

For example:

```tsx
"use server";

export async function deleteProduct(id: string) {
	try {
		await db.product.delete({
			where: { id },
		});

		return {
			success: true,
		};
	} catch {
		return {
			error: "Unable to delete product",
		};
	}
}
```

The UI can then display the returned error.

---

# 16. Expected Errors vs Unexpected Errors

Not every error should be handled in exactly the same way.

### Expected Error

For example:

```text
Email already exists
Invalid input
Product does not exist
```

These can often be returned as part of the action result:

```tsx
return {
	error: "Email already exists",
};
```

### Unexpected Error

For example:

```text
Unexpected database failure
Programming error
Server infrastructure failure
```

These should be handled as actual exceptions and can be allowed to reach the application's error handling system when appropriate.

The important idea is:

```text
Expected problem
    ↓
Return useful form/action error

Unexpected failure
    ↓
Handle as application error
```

# 17. Revalidation After Mutations

After changing data, cached content may need to be updated. The full caching API — including when to use `revalidatePath`, `revalidateTag`, and `updateTag`

For example:

```text
/products
```

shows product data.

An admin updates a product:

```text
Database
   ↓
Product updated
```

But a cached route may still contain the previous result.

You can revalidate the affected route:

```tsx
"use server";

import { revalidatePath } from "next/cache";

export async function updateProduct(id: string, price: number) {
	await db.product.update({
		where: { id },
		data: { price },
	});

	revalidatePath("/products");
}
```

The flow becomes:

```text
Server Action
      ↓
Update Database
      ↓
Revalidate Cache
      ↓
Fresh Product Data
```

---

# 18. `revalidatePath()` After a Mutation

`revalidatePath()` targets a specific route.

Example:

```tsx
revalidatePath("/products");
```

This is useful when you know exactly which route needs fresh content.

For a dynamic product page:

```text
/products/[id]
```

you can revalidate the affected path:

```tsx
revalidatePath(`/products/${id}`);
```

For example:

```tsx
await db.product.update({
	where: { id },
	data: {
		price,
	},
});

revalidatePath(`/products/${id}`);
```

---

# 19. `revalidateTag()` After a Mutation

When the same data is used by multiple routes, cache tags can be useful.

For example, product data may be used by:

```text
/products
/products/123
/search
/home
```

The data can be fetched with a tag:

```tsx
const response = await fetch("https://api.example.com/products", {
	next: {
		tags: ["products"],
	},
});
```

After a mutation:

```tsx
import { revalidateTag } from "next/cache";

revalidateTag("products", "max");
```

The concept is:

```text
Update product
      ↓
Revalidate "products"
      ↓
Related cached data can be refreshed
```

> `revalidateTag(tag, "max")` marks tagged data stale and refreshes on the next visit — it does not purge the cache immediately. See Caching & Revalidation for full semantics.

---

# 20. `updateTag()` for Immediate Updates

When an admin creates or edits a product and should **see the change right away** (read-your-own-writes), use **`updateTag`** instead of `revalidateTag`. It can only be called from Server Actions and makes the next request wait for fresh data rather than serving stale content.

```tsx
"use server";

import { updateTag } from "next/cache";
import { redirect } from "next/navigation";

export async function createProduct(formData: FormData) {
	const product = await db.product.create({
		data: {
			name: String(formData.get("name")),
			price: Number(formData.get("price")),
		},
	});

	updateTag("products");
	updateTag(`product-${product.id}`);

	redirect(`/products/${product.id}`);
}
```

Use **`updateTag`** when the same user who mutated data should see fresh content immediately. Use **`revalidateTag(tag, "max")`** when a slight delay is acceptable (background refresh on next visit). Details in **Caching & Revalidation** (`updateTag()` for Immediate Updates).

# 21. Redirecting After a Mutation

After a successful mutation, the user may need to be sent to another page.

For example:

```text
Create Product
      ↓
Success
      ↓
/products
```

A Server Action can use `redirect()`:

```tsx
"use server";

import { redirect } from "next/navigation";

export async function createProduct(formData: FormData) {
	// Create product

	redirect("/products");
}
```

> **`redirect()` throws internally** — call it outside `try/catch`, or re-throw with `isRedirectError`.

The flow becomes:

```text
Submit
  ↓
Validate
  ↓
Create
  ↓
Revalidate
  ↓
Redirect
```

Example:

```tsx
"use server";

import { revalidatePath } from "next/cache";

import { redirect } from "next/navigation";

export async function createProduct(formData: FormData) {
	// Validate data

	await db.product.create({
		data: {
			// ...
		},
	});

	revalidatePath("/products");

	redirect("/products");
}
```

# 22. Server Actions vs Client-Side API Calls

There are two common ways to perform a mutation from a Next.js application.

### Server Action

```text
Form / Client
      ↓
Server Action
      ↓
Database
```

### Client-Side API Call

```text
Client
   ↓
fetch()
   ↓
API endpoint
   ↓
Server
   ↓
Database
```

Both approaches are useful.

# 25. When to Use Server Actions

Server Actions are a good choice when:

- The mutation is part of your Next.js application.
- A form needs server-side processing.
- You do not need a public API endpoint.
- You want to keep form mutation logic on the server.
- The UI and server logic belong to the same application.

Examples:

```text
Create account
Update profile
Create product
Update settings
Delete item
Submit feedback
```

---

# 26. When to Use Client-Side API Calls

Client-side API calls can be a better choice when:

- Multiple clients need the same API.
- A mobile application consumes the backend.
- A separate frontend needs the backend.
- You are building a public or external API.
- The API needs independent versioning.
- Other services need to consume the endpoint.

For example:

```text
Next.js Web App
       ↓
       API
      ↙   ↘
Mobile    Other Client
App
```

In this architecture, an API endpoint is often more appropriate than a Server Action.

---

# 27. Server Actions vs API Routes

| Server Actions                              | API Routes / Route Handlers       |
| ------------------------------------------- | --------------------------------- |
| Convenient for application mutations        | Better for explicit API endpoints |
| Excellent for forms                         | Useful for multiple API consumers |
| Server-side function abstraction            | HTTP endpoint                     |
| Less API boilerplate for internal mutations | Easy to consume from any client   |
| Closely integrated with Next.js UI          | More independent from UI          |

A simple decision:

```text
Only Next.js application needs the mutation?
        ↓
Server Action

Multiple clients need the endpoint?
        ↓
API / Route Handler
```

# 28. Complete Server Action Flow

A production form can follow this pattern:

```text
User
 ↓
Form
 ↓
Client validation
 ↓
Submit
 ↓
Server Action
 ↓
Authentication
 ↓
Authorization
 ↓
Server validation
 ↓
Database mutation
 ↓
Revalidate cache
 ↓
Return result / Redirect
```

For example:

```text
Create Product
      ↓
Check user is logged in
      ↓
Check user can create products
      ↓
Validate product data
      ↓
Insert into database
      ↓
Revalidate /products
      ↓
Redirect to /products
```

# 29. Authentication and Authorization

Server Actions should not assume that the caller is allowed to perform an operation.

A Server Action is a callable HTTP POST endpoint regardless of whether any page links to it — skipping the auth check exposes it as a public endpoint even with no UI calling it.

For example:

```text
Delete Product
```

should not simply do:

```tsx
await db.product.delete(...);
```

The server should first check:

```text
Is user authenticated?
        ↓
Is user authorized?
        ↓
Can this user delete this product?
```

Conceptually:

```text
Server Action
     ↓
Authentication
     ↓
Authorization
     ↓
Validation
     ↓
Mutation
```

These checks belong on the server because client-side checks can be bypassed.

# 30. Common Mistakes

## Mistake 1: Trusting Client Validation

Do not rely only on:

```text
React Hook Form
```

or:

```text
Browser validation
```

The Server Action must validate the submitted data.

---

## Mistake 2: Forgetting Authorization

Authentication answers:

```text
Who is the user?
```

Authorization answers:

```text
Is this user allowed to perform this action?
```

Both can matter for mutations.

---

## Mistake 3: Updating the Database but Not Revalidating

Suppose:

```text
Database = updated
Cache = old
```

The UI may continue showing old data.

Use an appropriate revalidation strategy when cached content needs to be refreshed.

---

## Mistake 4: Returning Sensitive Information

Do not return sensitive server-side information to the client.

For example, avoid returning:

```text
Database credentials
Internal errors
Private tokens
Sensitive user data
```

Return only the information the UI actually needs.

---

## Mistake 5: Using Server Actions for Every API Requirement

Server Actions are not a replacement for every API endpoint.

If:

```text
Mobile app
Web app
Third-party client
```

all need the same backend API, an explicit API may be more appropriate.

---

## Mistake 6: Putting Large Amounts of Client Logic in the Form

Keep server-side mutation logic on the server.

The client should mainly handle:

```text
UI
User interaction
Client-side feedback
```

The server should handle:

```text
Authentication
Authorization
Validation
Database mutation
Sensitive logic
```

---

# 31. Best Practices

### 1. Validate on the Server

Always validate data before performing a mutation.

```text
FormData
 ↓
Validation
 ↓
Mutation
```

---

### 2. Check Authorization

Before changing data:

```text
Authentication
      ↓
Authorization
      ↓
Mutation
```

---

### 3. Keep Server-Only Logic on the Server

Database operations, secrets, and sensitive business logic should remain server-side.

---

### 4. Revalidate After Mutations

If the mutation changes cached data:

```tsx
revalidatePath("/products");
```

or use an appropriate cache-tag strategy.

---

### 5. Return Useful Errors

Instead of:

```text
Error
```

return useful information:

```text
Email already exists
Invalid product price
Product not found
```

Do not expose sensitive internal details.

---

### 6. Redirect After Successful Mutations When Appropriate

For example:

```text
Create Product
     ↓
Success
     ↓
/products
```

Use:

```tsx
redirect("/products");
```

when that matches the desired user flow.

---

### 7. Use Server Actions for the Right Job

Use them mainly for server-side mutations and form processing inside the Next.js application.

Use API endpoints when multiple clients or external consumers need the same HTTP API.

# 32. Quick Comparison

| Topic                  | Purpose                                                      |
| ---------------------- | ------------------------------------------------------------ |
| Server Actions         | Execute server-side functions                                |
| `"use server"`         | Mark server-side action code                                 |
| Forms                  | Trigger Server Actions conveniently                          |
| `.bind()`              | Pass extra arguments to a form action                        |
| Server-Side Mutations  | Create, update, or delete server data                        |
| Validation             | Verify submitted data                                        |
| `useActionState`       | Receive action return values in Client Components            |
| RHF + `useActionState` | Client validation via RHF, server errors via `formAction`    |
| `updateTag()`          | Immediate cache update after mutation (read-your-own-writes) |
| Error Handling         | Return or handle expected and unexpected failures            |
| `revalidatePath()`     | Revalidate a specific route                                  |
| `revalidateTag()`      | Revalidate tagged cached data                                |
| `redirect()`           | Navigate after a successful operation                        |
| API Calls              | Communicate through explicit HTTP endpoints                  |

# Summary

- Server Actions allow server-side functions to be invoked from the application.
- `"use server"` marks server-side action code — at file level or inside a single function.
- Forms are one of the most common uses of Server Actions; use `.bind()` when the action needs extra arguments beyond `FormData`.
- **`useActionState`** connects a Server Action's return value to a Client Component — pass `formAction` to the form, not the raw action.
- With **React Hook Form**, use `handleSubmit` + `startTransition(() => formAction(fd))` instead of `<form action>`.
- **`updateTag`** gives immediate cache freshness after a mutation when the same user should see their change right away; **`revalidateTag(tag, "max")`** is for stale-while-revalidate on the next visit.
- Server Actions can also be called outside forms (e.g. button clicks) via `startTransition`.
- Server Actions are useful for server-side mutations such as create, update, and delete operations.
- Form data can be received through `FormData`.
- Always validate data inside the Server Action before performing a mutation.
- Client-side validation improves user experience but cannot replace server-side validation.
- Authentication and authorization must be checked on the server — a Server Action is a callable endpoint even without UI linking to it.
- Expected errors can be returned as structured action results.
- Unexpected errors should be handled as application errors rather than exposed as sensitive details.
- After a mutation, cached data may need to be revalidated.
- `revalidatePath()` is useful when a specific route needs to be refreshed.
- `revalidateTag()` is useful when related cached data is shared across multiple routes.
- `redirect()` can be used after a successful mutation when the user should move to another route.
- Server Actions can simplify mutations that belong only to the Next.js application.
- Client-side API calls and API endpoints are often more appropriate when multiple clients need the same backend API.
- Server Actions are not a replacement for every API endpoint.

## Quick Decision Guide

```text
Need to submit a form?
        ↓
Server Action can be a good choice

Need to create/update/delete data?
        ↓
Server Action can handle the mutation

Need validation?
        ↓
Validate inside the Server Action

Need admin to see their edit immediately?
        ↓
updateTag() in the Server Action (Caching & Revalidation for details)

Need to show server errors in the UI?
        ↓
useActionState + return errors from Server Action

Using React Hook Form for client validation?
        ↓
handleSubmit → build FormData → startTransition(() => formAction(fd))
(show both RHF errors and state.errors)

Need to pass an id to an update action?
        ↓
.bind(null, id)

Need authentication?
        ↓
Check the user on the server

Need authorization?
        ↓
Check permissions before mutation

Changed cached data?
        ↓
Revalidate affected path or tag

Need to send the user somewhere after success?
        ↓
redirect()

Need the same API for mobile, web, or external clients?
        ↓
Consider an API / Route Handler
```

> **Simple rule:** Use Server Actions to keep application mutations close to the server-side logic, validate and authorize every mutation on the server, revalidate affected cached data, and use explicit APIs when multiple clients need the same backend service.
